# KunPlayer 实施计划

> 目标设备：小米电视4A 58"，Android 6.0.1（API 23），Amlogic T962 四核 A53 @1.5GHz，2GB RAM，第三方桌面。
> 用途：自己用。不追求上架，不追求与 B 站官方客户端功能对齐。

## 一、已锁定的决策

| 项 | 结论 | 理由 |
|---|---|---|
| 语言/UI | Kotlin + View + RecyclerView（Leanback 的 `ListRow` 思路，不用 Compose） | T962 上 Compose 重组掉帧，没有任何调优余地 |
| 播放 | Media3 ExoPlayer + `OkHttpDataSource`，纯音频走 `ProgressiveMediaSource` | 音轨本身就是完整 m4a，省掉 DASH 解析；Referer 可逐请求注入 |
| 网络 | OkHttp（接口与取流共用同一实例） | CDN 校验 Referer/UA，WebView 做不到 |
| 配置 | `minSdk 23` / `targetSdk 28` / `compileSdk 35` | 老设备上高 targetSdk 只换来新限制 |
| 缓存 | 首屏 JSON 文件 + 临时文件换名，不引入 Room | 断电安全，体积零成本 |
| 首页 | 推荐流（`from_region=1003` 音乐分区，15 卡/行） | 开电视到出声最短 |
| 队列语义 | 按 OK 立即播，整行 15 首入队；长按 OK 进详情 | 推荐流本身就是播放队列 |
| 命名/视觉 | KunPlayer，主题橙 `#FF8A3D`，底 `#0E1215` | 与 B 站粉色无关联，规避商标 |

## 二、静态审计结论（已完成）

上一版计划把「复用 bv 的 bili-api」列为高风险，理由有三条。逐条读源码后，三条全部证伪：

| 原判断 | 实际情况 | 依据 |
|---|---|---|
| 音轨能否取到未知 | 确定能取 | `PlayUrlData.dash` 有 `audio`/`dolby`/`flac`，`DashData` 含 `base_url` |
| Cookie 必须共享给 OkHttp，否则 403 | 不需要 | 接口层把 `sessData`/`mid` 当显式参数传；媒体请求只挂 Referer+UA |
| Android 6 TLS 要自己挂 Conscrypt | 不需要 | bv 的 `OkHttpUtil` 已内置 GlobalSign ECC Root CA R5 |
| — | 纯音频播放器零改动 | `ExoMediaPlayer.playUrl(videoUrl: String?, audioUrl: String?)` 传 null 即纯音频 |
| — | minSdk 覆盖目标设备 | bv `AppConfiguration.minSdk = 23` |

**必须打的两个补丁**（本仓库已修，见 `model/BiliModels.kt`）：

1. `DashData.backupUrl` 缺 `@SerialName("backup_url")` —— 上游该字段永远是空列表，备份 CDN 切换实际失效；
2. 音频条目的 `width/height/frame_rate/sar` 无非空默认值 —— 缺字段会整条反序列化失败。

**依赖策略**：本阶段**不引入** bv 的 `bili-api`（Ktor + Koin/KSP + gRPC/protobuf + Jsoup，估算 +4MB 且启动变慢），
四个接口手写 OK。Phase 2 补齐 8~10 个接口后若手写成本超过收益，再评估引入并裁掉 gRPC 分支——
这是独立决策，不阻塞探针。

## 三、阶段

### Phase 0 · 链路探针（已完成）

一个页面一个按钮，跑完 `finger/spi → nav → view → playurl → 出声`。四项问答的真机结果：

- [x] 新设备首发请求未被 412 卡住：buvid 激活有效，不需要 App 端 UA 或 `access_key`
- [x] Android 6 的 TLS 能握手：不需要挂 Conscrypt
- [x] `playurl` 返回 `dash.audio`：WBI 签名一次通过，未走非签名回退
- [x] 带 Referer 的 ExoPlayer 真的出声：6 秒后进度 3204ms

**验收达成**：日志出现「✅ 出声成功」，Cookie 里有 buvid3/buvid4。
顺带确认：未登录最高只有 203kbps AAC（FLAC 需登录），对电视外放无差别，登录留到 Phase 2。

### Phase 1 · 骨架与焦点（已完成）

- 首页 = **音乐区排行榜**（`ranking/v2?rid=3`，97 首，条目自带 `cid`）+ 15 卡/行
- 焦点：1.08 缩放、6dp→12dp 抬升、橙色描边；焦点位置落 SharedPreferences，重启回到原卡
- 首屏缓存：`FeedCache`（JSON + renameTo，TTL 30 分钟）；命中缓存时冷启动零网络请求（0.11 已删除，不再预热）
- 遥控器：左右移卡、上下换批（共 7 批，循环）、OK 播整行、对当前曲目再按 OK 暂停
- 顺手做了最小播放：队列自动连播、底部正在播放条、暂停时进度线转灰

**验收达成**：`am start -W` 冷启动 561ms；断网时走缓存照样出画面；左右到末位不丢焦点。

与计划的偏差及原因：

| 原计划 | 实际 | 原因 |
|---|---|---|
| 首页用推荐流 `from_region=1003` | 音乐区排行榜 | 推荐流 20 条里混着新闻、美食、游戏，在音乐播放器里按 OK 播出一条新闻是荒诞的；排行榜条目还自带 `cid`，省掉每首一次 view |
| 15 卡一行 + 上下键空置 | 上下键 = 换一批 | 单行布局里上下键若是死键，用户会以为遥控器坏了 |
| 播放页留到 Phase 3 | 先做了最小播放 | `AudioPlayer` + `pickAudio` 已在 Phase 0 验证过，接上去只多 80 行，让首页当场可用 |


### Phase 2 · 导航与多行货架（已完成）

首页从「单行换批」改成「左侧导航 + 多行货架」，因为收藏夹一进来单行就放不下了。

- 数据：`ranking/v2?rid=3`（97 首）按 `tname` 切行 → 音乐排行榜 / 音乐综合 / 演奏 / 翻唱 /
  VOCALOID / MV / 原创音乐 / 音乐现场 / 乐评盘点；`newlist?rid=3` 兜「最新投稿」行
- 导航：「发现 / 收藏」，选中态是橙色竖条，焦点态是圆角底；两者分开画，否则分不清「我停在这」和「我在这」
- 焦点路由（`dispatchKeyEvent` 显式路由，不靠 `focusSearch`）：
  行内左右 → 行间上下 → 首列向左进导航 → 末行向下进播放条 → 播放条向上回原行
- 每行各自记住列位；进程重启回到原来那一行那一张卡
- 收藏：MENU 键本地收藏，收藏页即队列；收藏为空时内容区中央给常驻空态
- 底部播放条：标题 + 时间 + 上一首/播放暂停/下一首三个可聚焦按钮

**验收达成**：冷启动 728ms 命中缓存零请求；杀进程重启回到 `row=2 col=3` 且卡片完整可见；
行首/行尾/首行/末行均不丢焦点；收藏空态与「已加入收藏」提示分属两个 View，互不擦除。

与计划的偏差及原因：

| 原计划 | 实际 | 原因 |
|---|---|---|
| 子分区用 `newlist?rid=28/31/…` 拉 | `newlist` 子分区全空，改用排行榜条目的 `tname` 分组 | 子分区接口返回空数组，`ranking/v2` 只认 rid=3；`tname` 反而更准（条目自带分类） |
| 用左右键切换分页 | 分成多行，上下键走行 | 多行货架下「上/下」是天然的层级导航，不需要再造分页 |
| 边缘渐隐遮罩 | 不做 | `wrap_content` 容器里放 `match_parent` 遮罩会被测量成整块高度，把布局撑出屏幕；卡片在容器边界被切断本来就是 TV 货架常态 |

### Phase 3 · 仿 tvOS Apple Music 视觉重做（已完成）

原来那版是「左侧深色侧栏 + 卡片底板」，功能齐但气质是通用 Android TV。这一版按 Apple TV 上
Apple Music 的语言重排，目标是打开就认得出是那套东西。

- 导航从左侧栏搬到**顶部文字页签**：内容区宽度从 790dp 回到 960dp，一行才放得下五张方形封面
- Hero：48dp 内缩圆角大卡，标题 + 艺人 + 白色胶囊「播放」，整块一个焦点单位
- 货架：裸封面（1:1）+ 标题 + 艺人，去掉卡片底板；封面按 1:1 向 CDN 重新要（`FeedApi.reCrop`）
- 焦点：整格放大 1.06 + 封面在框内再放大 1.06（视差）+ 白描边淡入，三层一起上
- 配色：纯黑底、`#8E8E93` 次文字、Apple Music 红 `#FA233B` 只用于进度条
- 播放条：透明黑 + 顶部 1dp 分割线，按钮聚焦是白底黑图标

**验收达成**：冷启动 476ms；冷启动一律落 Hero（不再恢复上次的行）；掉帧率 8.6%（90 分位 16ms）。

> Phase 2 那版「进程重启回到原来那一行」这次被撤掉了。加了 Hero 之后，恢复深行意味着第二次
> 以后打开永远见不到 Hero，而那正是这一版最像 tvOS 的一块。行内列位仍保留在本次会话内。

三处只能接近、无法等同（写进 `AGENTS.md`，不要在 review 里当 bug）：
SF Pro 不能打包、specular highlight 做不了（改固定角度双层白描边）、实时毛玻璃换成预渲染。

实现时踩到并修掉的三处：

| 症状 | 原因 | 修法 |
|---|---|---|
| 启动就滚到货架，Hero 被顶出屏幕 | `revealShelf` 为了让第一行「完整露出」滚了 290dp | 首次进入且记忆位置在第一行时，焦点给 Hero 且不滚 |
| 换行后 Hero 圆角残影挂在页签下 / 行滚不出来 | `shelf.root.top` 是相对 shelfBox 的坐标，没算 Hero 的高度 | 用 `shelfBox.top + root.top`，并且贴齐 top 滚不留边 |
| 页签上按右会把列表里某首播了 | 页签的左右键交给了系统 focusSearch，焦点翻进内容区 | 页签自己吃掉四个方向，左右只在自己的项之间移动 |

### Phase 4 · 接口层补齐（已完成）

| 接口 | 路径 | 实测结论 |
|---|---|---|
| 排行榜 | `ranking/v2?rid=3` | ✅ 64 首（不同时段 60~97），带 `cid`，未签名可用 |
| 分区最新 | `newlist?rid=3` | ✅ 27 首 |
| 搜索 | `wbi/search/type` | ✅ 未登录可用，30 条/页。**拼音直通**：`zhoujielun` 与「周杰伦」返回同一批结果 |
| 收藏夹列表 | `v3/fav/folder/created/list-all` | ✅ 需登录，返回 2 个夹子（含 `attr=22` 的私密夹） |
| 收藏内容 | `v3/fav/resource/list` | ✅ 默认夹 14 条里 10 条有效（`attr≠0` 是失效稿件） |
| 历史 | `web-interface/history/cursor` | ✅ 需登录，自带 `cid`。**不能带 `type=video`**，带上直接 -400 |
| 心跳 | `click-interface/web/heartbeat` | ✅ POST + `csrf=bili_jct`，15 秒一次，服务端 `progress` 与实播秒数一致 |
| 扫码登录 | `passport-login/web/qrcode/*` | ✅ 生成 + 轮询（1.5s）。**登录态走 Set-Cookie 下发**，`data.url` 只有部分参数 |

**验收达成**：排行 / 最新 / 搜索 / 收藏 / 历史五项都进得了列表；登录后 nav 的 `isLogin=true`，
杀进程重启仍是「老K在此逛逛」（Cookie 落 SharedPreferences + 保留 buvid 指纹）。

界面随之扩成五个页签：

- 搜索页 → 自绘 QWERTY（只有 a-z）+ 结果紧凑货架（132dp 封面，给键盘让出 225dp）
- 收藏页 → 登录后是云端收藏夹（一夹一行，取前 5 个夹子、每夹 20 条）；未登录退回本地收藏
- 历史页 → 最近播放 30 条，标题优先取 `show_title`（多 P 合集里那才是歌名）
- 我的 → 登录状态与扫码入口。登录入口只放这一处，不散在收藏页与历史页

真机上踩到并修掉的六处（每条都写进了对应代码的注释）：

| 症状 | 原因 | 修法 |
|---|---|---|
| 扫码确认后提示「Cookie 未落地」 | 只从 poll 的 `data.url` 抠 Cookie，真机上登录态主要走响应头 | `HttpResult` 把 Set-Cookie 一起带出来，两条路都读 |
| 历史 -400「请求错误」 | `type=video` 不是合法参数 | 去掉；不带时默认只返回 archive |
| 心跳一行红字、历史永远不涨 | 心跳跑在 Handler 主线程 → NetworkOnMainThread | 改成 IO 协程；切歌 cancel，暂停停表 |
| 点「扫码登录」毫无反应 | 焦点路由的 `return true` 把确认键一起吞了 | 面板分支只吃方向键，确认键放行 |
| 历史页卡片和「还没有播放记录」叠在一起 | 异步加载先摆空态，数据回来没清 | `renderShelves` 有内容就清空态 |
| 冷启动从 0.5s 涨到 1.1s | 27 个键逐个 inflate | 第一次进搜索页才铺键盘 |

最终启动耗时：应用侧 onCreate 145ms（布局 45 / 绑定 30 / 首屏 70），进程冷启到首帧约 1.0s，
剩下的都在系统侧（这台机器的进程 fork 本身就慢），不是这一版引入的。

> 搜索键盘只有 a-z 不是妥协，是结论：B 站搜索服务本身吃拼音。不做汉字输入法、不做候选词，
> 是搜索页在遥控器上真正可用的前提。

### Phase 5 · 播放页与队列（已完成）

三块：全屏播放页、队列模式、前台服务。前提是一处结构调整——播放器从「Activity 的成员」
提升成进程内单例（`PlaybackController.get(context)`），界面通过 `addListener` 订阅状态。
不这么改，界面一销毁播放就没了，后台播放根本无从谈起。

**播放页**（`ui/NowPlaying.kt` + `res/layout/overlay_now.xml`）

- 背景是当前封面放大后的模糊。**没用 RenderScript**：`ScriptIntrinsicBlur` 在 API 31 已废弃，
  还要单独引 `androidx.renderscript`。改成在 96×54 上做三轮箱式模糊（半径 2）再双线性放大 5 倍——
  相对半径足够大，放大后是一块干净光斑。6 次遍历约 3 万像素操作，A53 上不到 2ms，可直接在主线程跑。
  按 bvid 缓存 4 张（480×270，约 500KB/张）。
- 版式：左上「正在播放」、右上队列位次（3 / 24）、236dp 方形封面、右侧歌名（34sp，最多两行）
  与 UP 主、4dp 进度线与两侧时间，底部五个控制键。「封面 + 信息 + 控制」整块竖向居中，
  而不是控制栏钉底——540dp 高的屏上钉底会在中间留出 130dp 的空带，看着像没画完。
- 焦点只在五个键之间横走，上下不出去。漏出去就会把焦点交回货架，画面还停在播放页，
  人一按就切走了歌。
- 入口是播放条最右端的向上折角：一路右按到底就能到，不必记某个功能键。
- **歌词没做**：B 站字幕接口在音乐区基本是空的，少数有 CC 的也是 UP 主口播稿，做出来是错的字。
  宁可留白，不做假歌词。

**队列**（`player/PlaybackController.kt`）

- 顺序 / 单曲 / 随机，写在 SharedPreferences 里，重启后保持。
- 单曲循环不重新取流：`seekTo(0)` + `resume()`。重取流每循环一次就多打一次 playurl，
  中间那段缓冲空档听得出来。
- 随机不与上一首重复（只剩两首时直接取另一首）。
- 取流结果缓存 30 分钟：单曲循环、来回上一首都省掉一次 WBI 签名。

**前台服务**（`player/PlaybackService.kt`）

- 起播时才拉起服务并转前台（`PlaybackController.playQueue` 里触发），没在放歌就不挂常驻通知。
  放在起播点而不是 Activity，是因为起播入口有 Hero、卡片、搜索结果三处，漏一处就会出现
  「从这条路径播的歌，回桌面就断」。
- 通知带上一首 / 播放暂停 / 下一首三个动作；`MediaSession` 同时暴露给系统。
- 播放状态由 Service 订阅得到，界面只是另一个订阅者，两者互不知道对方存在。

**备份 CDN**

`playurl` 给每条音轨 2~4 个备份域名。播放器报错时按 `base_url → backup_url[0..n]` 依次重试，
全部失败才算这一首取不到，并清掉取流缓存（地址很可能已经过期）。

**真机验收**

| 项 | 结果 |
|---|---|
| 连切 24 首 | 0 次取流异常、0 次播放错误；`TOTAL` 94.2MB → 94.0MB（Dalvik 堆涨到 40MB 后由封面缓存封顶，堆上限 512MB） |
| 回桌面 3 分钟 | 进程存活；`ServiceRecord` 在（createdFromFg=true）；`MediaSession` state=3；通知 id=1001 带 3 个动作 |
| 待机 10 分钟 | 12:52 回桌面 → 13:03 仍在播，pid 未变；期间两首自然播完并各自在 0.5s 内自动续到下一首；`FATAL` 0 条 |
| 回到前台 | 播放条按 snapshot 恢复歌名与时间，进度未回退 |
| 冷启动 | 应用侧 145ms、进程到首帧 1.0s，与上一版持平 |

**踩到的坑**

| 症状 | 原因 | 修法 |
|---|---|---|
| 播放页标题永远空白 | 播放页和播放条都叫 `now_title`，同一布局里 `findViewById` 只认先出现的那个 | 播放页全部 id 加 `player_` 前缀 |
| 五个控制键全都按不动 | `dispatchKeyEvent` 里 `return false` 只是「我不认」，事件不会自动漏下去 | 不认的键显式 `return super.dispatchKeyEvent(event)` |
| 封面圆角没裁出来 | 只给了背景，没 `clipToOutline` | 补上，圆角由 bg 的 outline 提供 |
| 播放页中间空一大片 | 控制栏钉底 | 整块竖向居中 |

### Phase 6 · 打磨与安装（已完成）

**签名**（`app/build.gradle.kts` + `keystore/`）

- release 不再借用 debug keystore。debug key 由 Android Studio 按机器生成，重装开发环境
  或换机器就会变，之后的包再也盖不上旧包（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`），
  只能卸载重装——而卸载会把登录态一起带走。
- 独立 jks（RSA 2048，有效期 30 年），口令放 `keystore.properties`，两个文件都进 `.gitignore`。
  配置缺失时不报错、回落 debug 签名，但会在构建日志里留一条显眼警告：
  静默回落比构建失败更危险——包看着正常，装的时候才发现签名不匹配。
- 同时开 v1 + v2 签名：这台电视是 Android 6，只认 v2 的包它装不上。

**签名迁移**（一次性，实测踩完了全过程）

设备上原本是 debug 签名的包。`pm uninstall -k` 保数据卸载**不解决问题**：
`-k` 会保留 packages.xml 里的签名记录，安装新签名包照样报 UPDATE_INCOMPATIBLE。
必须整包卸载，于是数据要靠 adb 搬：

```
run-as 打包 → pm uninstall → 装一个临时 debuggable 的 release 包 → run-as 解包还原
→ 换成正式 release 包 install -r
```

还原后 `登录态：true（老K在此逛逛）`、本地收藏、队列模式全部还在。
中间那一步"临时 debuggable"是必须的：正式包不可调试，`run-as` 用不了，数据塞不回去。

**为什么正式包保留 `isDebuggable = true`**

这是自己 adb 装的包，不是上架包。代价只是别人能 `run-as` 读它的数据；收益是诊断链路完整——
`adb exec-out run-as com.kunplayer.tv cat files/diag.log` 能直接拿埋点、崩溃记录、
SharedPreferences。关掉它，这些文件就躺在 `/data/data` 里谁也读不到，等于白记。
上架或对外分发前必须改回 false。

外置目录（`/sdcard/Android/data/<包名>`）试过，这台机器上不可行：小米把这个目录建成
`root:sdcard_rw 771`，应用既不是属主也不在组里，连 files 子目录都建不出来；
要写得通就得申请存储权限，为一个日志弹权限框不值。

**焦点埋点**（`diag/Diag.kt`）

只记一个指标：**从焦点落进某个区域到按下确认，中间隔了几次方向键、多少毫秒。**

理由是电视端和手机端的差别：遥控器只有五个方向键加一个确认，没有「滑一下就到」。
一个控件如果要点六下才够得着，手机上只是稍烦，电视上就是「这功能坏了」。
所以日志只有两种行，都带这两个数：

```
离开 播放条 · 停留 5965ms · 5键
确认 卡片起播 第2行第3张《20世纪美国乡村…》 @第2行 · 自进入 5418ms · 2键
```

- 区域用业务语言命名（Hero / 第N行 / 播放条 / 播放页按键 / 播放页进度条 / 键盘 / 页签），
  不用控件 id——半年后看日志，`row_list_3` 认不出来是什么。
- 按 32 条一批落盘，`onStop` 与 `onDestroy` 时把尾巴写掉。只留 128KB，超了留一代旧文件：
  电视的 `/data` 分区本来就小，日志吃满空间会被系统清应用数据。
- 调试包里同一份内容也进 logcat（`BuildConfig.DEBUG`），现场排查比 cat 文件快。

**崩溃日志**（`diag/Crash.kt`）

- `Crash.install()` 是 `KunApp.onCreate` 的第一行，早于 CookieStore/BiliHttp：
  装在它们后面，那两步里出的错就抓不到。
- 文件里是版本、设备、线程、完整异常链，**外加崩溃前最后 40 条焦点/确认记录**。
  只有堆栈的话，一个空指针到底是他按了搜索还是切了页签，根本无从判断。
- 只留最近 5 份。重复崩溃会迅速写满 `/data`，而 `/data` 满了系统直接清应用数据，
  那等于把登录态一起丢掉，比崩溃本身更难解释。
- 「我的」页在存在崩溃文件时显示一行 `异常记录 N 份 · 按 MENU 清除`，没有就不占位。

**播放页进度条可聚焦**（`ui/NowPlaying.kt`）

- 遥控器左右 = 快退/快进 5 秒；确认 = 播放/暂停；下 = 回按键行；上 = 回进度条。
  改之前这一页除了切歌没有任何"跳到某一段"的办法，而想听副歌是纯音频最常见的诉求。
- 焦点热区 28dp、视觉仍 4dp：热区做厚了这条线在画面里会显得笨重。
- 聚焦时浮出白色拖动点与一层极淡的胶囊底板，时间文字转白。
- 跳转后 700ms 内以目标位置为准显示。播放器 seek 完的 position 有一小段是旧的，
  照实画会让进度条往回跳一下，连按几次就是一连串抖动。

**长按确认键收藏**（`MainActivity.holdToFavorite`）

- 收藏原本只能按 MENU，而 MENU 不是每支遥控都有（手机遥控 App、蓝牙小遥控基本没有）。
- 按住方向键/确认键时系统**不会**回调 `onLongClick`——那是触摸才有的路径，必须自己判。
  两条判定并存：系统重复事件（`isLongPress`/`repeatCount`）先到就用它，600ms 计时器兜底。
  只剩计时器的话，不自动重复的遥控就废了；只剩重复事件的话，注入的按键测不了。
- 长按触发后要把随后的抬起吞掉，否则「收藏完立刻起播」。
- 计时用独立 Handler：`hint()` 里那句 `removeCallbacksAndMessages(null)` 会顺手清掉
  主 Handler 上的长按计时，表现为「有时能收藏、有时不能」。

| 项 | 结果 |
|---|---|
| 签名 | `apksigner` 显示 `CN=KunPlayer`；`install -r` 覆盖安装成功且数据保留 |

**踩到的坑**

| 症状 | 原因 | 修法 |
|---|---|---|
| 按住下键到不了底，行号会往回退 | 迟到的焦点回调把 `currentShelf` 改回旧行，下一次按键从旧行起算 | `currentShelf` 只由导航写，焦点回调只在行号相符时才更新 |
| 按十下方向键，实际只走两三行 | 每次按键都往下一帧排一个 `requestFocus`，十几个任务陆续落地，谁最后跑谁说了算 | 只保留最后一个目标（`pendingRow`），按键只改目标不排队 |
| 从卡片按下去到播放条，下一帧焦点又跳回卡片 | 排队的 `requestFocus` 不知道自己已经过时 | 落地前检查焦点是否还在内容区，不在就丢弃 |
| 播放条上按下键，画面莫名滚回中间某行 | 系统 `FocusFinder` 自己找「下方最近的控件」 | 播放条贴底，四个方向全自己吃 |
| 播放条右端再按右，焦点甩回货架 | 同上，末端交回系统就失控 | `moveBar()` 两端兜住 |
| release 构建被 lint 拦下 | `ExpiredTargetSdkVersion`（targetSdk 28 是刻意为之） | `lint { disable += "ExpiredTargetSdkVersion" }` |
| 埋点写出来了却取不出 | 写在 `/data/data` 私有目录，正式包不可调试 | 自用包保留 debuggable + `run-as` |
| 每条日志在 logcat 里出现两遍 | `line()` 打一次 `Log.i`，`write()` 在调试包里又打一次 | 只由 `write()` 负责 logcat |

### Phase 7 · 界面重做：从视频站骨架换成听歌界面（已完成）

**起因**：用户看完 0.7.0 的界面，一句话点破——「像是视频软件了，我要的是听歌界面」。

这个判断是对的，而且原因不在配色。把截图逐条拆开看，像视频站的是**骨架**：

| 视频站的骨架 | 它服务的行为 | 听歌里没有这个行为 |
|---|---|---|
| 列表带「播放量 / 时长」两列 | 判断这条值不值得点开 | 歌名和歌手就够了 |
| Hero 大 banner + 多行货架 | 逛、扫、发现新内容 | 一边听一边刷是视频的用法 |
| 底部横跨的播放条 | 边逛边放（浏览是主，播放是次） | 播放就是主界面 |
| 五个页签 + 逐级点击 | 功能多、分区多 | 只有「放这首」和「换一首」 |

四个叠在一起，就是一台视频客户端。要改的不是皮肤，是把这四样拆掉。

**参考对象**（只取结构，不抄视觉资产）：网易云音乐的播放页（一屏一首）、
QQ 音乐 TV 版的双栏（当前播放 + 队列）、汽水音乐的单曲流（上下切歌）。

**三个方案与选择**：

| 方案 | 结构 | 遥控器代价 | 找歌能力 |
|---|---|---|---|
| A 唱片机 | 模糊封面铺底，左封面右信息，全页无焦点移动 | 0 次换焦点 | 只能逐首跳，跨 30 首要按 29 下 |
| B 左唱针右队列 | 左栏当前播放，右栏队列列表 | 1 次进列表 | 列表直接选 |
| C 单曲流 | 满屏封面，上下翻 | 0 次 | 没有列表，只能搜 |

用户选了 **A + B**：播放页用 A 的唱片机形态，选歌用 B 的列表。落地的形态是「一屏主界面 +
上键唤出的歌单抽屉」，而不是两个并列的页面——两个并列页面会让「现在在听什么」在两处出现，
又回到视频站「列表 + 播放器」的两层结构。

**最终结构**（四层，见 README 的表格）：主屏 / 歌单抽屉（上键）/ 工具条（下键）/ 全屏页。

关键取舍：**主屏上方向键是动作，不是移动焦点**。整个主屏只有两个焦点位（封面、进度条），
左右切歌、确认暂停都由 `dispatchKeyEvent` 直接映射。焦点能省一次，遥控器就少按一次。

**歌单抽屉的来源行整行一个焦点**：五个来源做成一排标签，点选不移动焦点——
每个标签都可聚焦的话，换一次分类要按两下（先移进标签行、再移标签），而这两下不产生信息。

**踩坑**：

| 症状 | 原因 | 修法 |
|---|---|---|
| 连按两次上键打不开歌单 | 用 `seek.hasFocus()` 判断层级，而 `requestFocus` 要下一帧才落地，两键间隔 50ms 时读到的还是旧焦点 | 层级状态由派发按键的这一层同步记（`onSeek`），不读焦点 |
| 切来源后列表停在第 11 行 | 同一个 RecyclerView 复用，`submit` 不重置滚动位置 | `render()` 里 `scrollToPosition(0)` |
| 空态下进度条和三个键仍可指 | 没在播也照样画 | 空态把 seek 与 bar 设 INVISIBLE |
| 抽屉关闭后按键全部失灵 | 焦点在列表行上，行随抽屉一起 GONE，焦点悬空 | `hide()` 里回调宿主把焦点交回封面 |
| 工具条与主控件行重叠 | 两者都在屏幕底部一行的位置 | 工具条贴底（12dp），模式从底部移到顶栏右上角 |

**实测**（小米电视4A，2026-10-31）：

| 项 | 结果 |
|---|---|
| 冷启动首屏 | 134ms（0.7.0 为 148ms） |
| 内存 `TOTAL` | 69MB（此前 88MB） |
| 两上键 → 歌单 → 确认起播 | 通过 |
| 歌单左右换来源（排行榜 64 首 / 最新 / 收藏 / 历史） | 通过，列表回到顶部 |
| 搜索拼音 → 结果列表 → 起播 | 通过（`zhoujielun` 30 条原始结果、11 条可播） |
| 主屏左右切歌 | 连切 10 首 0 错误 |
| 进度条层左右快退快进 5 秒 | 通过，圆点出现、时间转白 |
| MENU 收藏 / 取消收藏 | 通过 |
| 返回键逐层收起，主屏退出 | 通过 |
| FATAL | 0 条 |

**这一版删掉的文件**：`ui/FeedAdapter.kt`、`res/layout/hero.xml`、`item_card.xml`、
`item_nav.xml`、`item_row.xml`。`model/Shelf.kt` 保留——取数接口仍返回「一组曲目 + 标题」，
只是界面不再把它画成一行货架。

### Phase 8 · 主屏按汽水音乐重排（已完成）

**起因**：用户给了两张汽水音乐的截图（桌面版 + 播放页），没有别的话。
意思很清楚——照着这个做。

0.8.0 的主屏虽然是「一屏一首歌」，排法还是播放器面板：左边一张封面、右边一列文字，
两块并排。看截图对了一下，差别不在配色，在**版面关系**：

| 汽水的播放页 | 0.8.0 的主屏 | 差的这一点意味着什么 |
|---|---|---|
| 封面居中，四周留白对称 | 封面靠左，右边一列字 | 居中 = 一张唱片；靠左 = 一个播放器窗口 |
| 文字左对齐在页面最左边 | 文字紧贴封面右侧 | 前者是「阅读顺序」，后者是「面板标注」 |
| 进度条通栏，从左到右贯穿 | 进度条只占文字列宽 | 通栏线是这张页面的地平线，整页靠它站住 |
| 播放键并进底部导航那一行 | 三个键单独占一行，缩在左下角 | 并进底栏就省下一整行，这一行给封面 |
| 背景接近纯深灰 | 满屏封面模糊大图 | 满屏大图是视频播放器的做法，它不承担信息 |

**落地**：

- 封面 224dp 居中、8dp 圆角，去掉 1dp 白描边（描边会把封面「框」起来）
- 歌名 28sp、最多两行、左对齐到进度条左端；歌手 16sp
- 进度条通栏 3dp，**白色**；红色只留给「已收藏」的心
- 底栏**一行**：左收藏心 / 中三键 / 右「顺序 · 1 / 64」
- 背景模糊降到 alpha 0.10，遮罩压到接近底色
- 空态：不画空封面框，两行居中文字

**为什么没照搬歌词区**：汽水在封面左侧铺歌词，B 站音乐区的字幕接口基本是空的
（少数有 CC 的也是 UP 主口播稿）。画不出来又不该留一块空白，所以文字挪到封面下方——
这也是这张页面和参考图唯一的排版差异。

**为什么文字左对齐**：这一版先试了居中（封面、歌名、歌手同一条中轴），
在真机上被长标题打回来了——「【Hi-Res】《许美静：月光之城》HI-END音响专业示范碟解码 96KHZ-24bit」
居中折成两行，第一行左端和第二行左端对不齐，读起来没有起点。左对齐至少能从头读。

**踩坑**：

| 症状 | 原因 | 修法 |
|---|---|---|
| 工具条打开时和播放键叠成一团 | 底栏挪到最底部后，工具条胶囊正好压在同一行 | 工具条打开时底栏淡出（`setBottomDimmed`） |
| 空态是一个空的灰色圆角方块 | 封面框还在，只是没图 | 空态把封面框 `GONE`，文字改居中 |
| 按键提示淡出时封面往下跳一格 | `GONE` 把那一行高度也拿掉了 | 淡出后改 `INVISIBLE`，留位置 |
| 时间看不出是多少 | 0.55 alpha 的 13sp 在白底上等于没有 | 提到 0.7 / 14sp，聚焦时 1.0 |

**实测**（小米电视4A，2026-10-31）：

| 项 | 结果 |
|---|---|
| 冷启动首屏 | 146ms |
| 内存 `TOTAL` | 99MB（连切十首后，此前口径 94MB） |
| 连切 10 首 | 0 错误，FATAL 0 条 |
| 进度条层快进 / 快退 | 通过，白点出现、时间转亮 |
| 工具条唤出 / 收起 | 通过，底栏让位、焦点回封面 |
| 歌单抽屉 | 通过（排行榜 64 首） |
| MENU 收藏 / 取消 | 通过，心形即时变色 |
| 空态（清掉队列后冷启动） | 两行居中文字，无空框 |

### Phase 9 · 首页：左侧导航 + 歌单详情（已完成）

**问题**：0.8/0.9 两版把主屏做成了一屏一首歌，找歌只能靠「上键唤出歌单抽屉」。
抽屉把五类歌单压在同一个列表里，每换一次来源都要先按几下方向键；搜索和我的
藏在「下键工具条」里。打开应用先看见封面、看不见「今天有什么歌」——
这不是听歌软件首页的样子，播放页才是那个样子。

**决策**：把「首页」和「播放页」当成两页，而不是把首页做成播放页的抽屉。

- 首页照汽水音乐桌面版：左边一列目的地，右边一张歌单详情，底下一条正在播放。
- 播放页（0.9 版）原样保留：一屏一首歌，方向键是动作。
- 抽屉与工具条删除，职责全部搬进首页侧栏——它们的五项来源本来就是首页的五个目的地。

**结构**（`res/layout/home_stage.xml`）：

| 区域 | 内容 |
|---|---|
| 侧栏 200dp | 今日推荐 / 正在收听 / 音乐排行榜 / 最新发布 · 我的音乐：我的收藏 / 播放历史 · 更多：搜索 / 我的 |
| 头部 | 封面 100dp + 标题 26sp + 一行说明 + 「播放全部」胶囊 + 共几首 |
| 列头 | # ／ 歌名 ／ 歌手 ／ 时长，与行内列宽一一对应 |
| 列表 | 行高 48dp，正在播的那首左侧一道红条 |
| 底栏 62dp | 封面 42dp + 歌名/歌手 + 收藏状态 + 三个键 + 播放模式 · 确认进播放页；进度压在底边 2dp |

**按键**（与播放页相反，这一页方向键是移动）：

| 键 | 动作 |
|---|---|

### Phase 10 · 今日推荐按 tname 分节（已完成）

**问题**：今日推荐是「排行榜 24 首 + 最新 12 首」混拼的一条 36 首长名单。没有分段，
滚到第 20 首时读不出「现在这一类是什么」，也看不出离下一类还有多远。而接口本来就
每条都带 tname（翻唱 / 演奏 / 音乐现场 / 原创音乐…），一次请求就能分开。

**决策**：把今日推荐做成**有节的歌单**，不引入第二种卡片形态。

- 第一节固定「热门」，取排行榜头部 10 首——推荐流要有入口，入口不能是某个小分类。
- 其余按 tname 分组，节内保持接口顺序，每节最多 12 首，最多 7 节。
- 少于 4 首的分组不出：两首歌撑不起一个标题。
- 同一首只归它第一次出现的节。重复会让「播放全部」把同一首播两遍。
- 音乐教学 / 电台 / AI 音乐不进推荐流，热门节也同样排除。
- 不插封面行、不做横滚货架：这个应用的推荐页是「一张能一路按到底的歌单」，
  不是必须横向浏览的卡片墙。

**实现**：

- `FeedApi.recommend()` 返回 `List<ShelfData>`（一节一个），取代原来的 `fetchShelves()`；
  后者与 `cache/FeedCache.kt` 早已没有调用方，一并删除。
- `ShelfData` 去掉没人用的 `compact`，语义从「货架的一行」改成「歌单里的一节」。
- `TrackListAdapter` 认两种行：节标题（不可聚焦）与歌。`submitSections()` 与 `submit()`
  并存，后者包装成「单节无标题」——其余五个目的地仍走同一套渲染。
- 序号在节内从 1 起；点击回调传扁平队列下标，不是 adapter position（分节后两者不等）。
- 回首页时若在播那首离节标题不超过 4 行，先对齐节标题再聚焦；否则它会贴在滚动区顶端，
  「这一节叫什么」被顶出屏幕，列表读起来像断了一截。

**实测**（小米电视4A，2026-10-31）：

| 项 | 结果 |
|---|---|
| 冷启动首屏 | 162ms |
| 内存 `TOTAL` | 36MB |
| 今日推荐 | 70 首 / 7 节：热门 10、翻唱 12、音乐现场 12… |
| 节内起播 | 通过：翻唱第 3 首 → 播放页「13 / 71」，队列下标正确 |
| 播放全部 | 通过：「1 / 70」，从热门第一首起 |
| 其余目的地 | 音乐排行榜 64 首，无节标题，序号从 1 起 |
| 返回首页 | 通过，焦点落在在播行，节标题同时可见 |
| FATAL | 0 条 |

**顺带补的焦点缺口**：底栏按上原来会跳回侧栏（中间整屏歌被跳过），列表末尾按下也不会
进底栏。现在只钉「列表末尾 ⇄ 底栏」这一段，侧栏内的上下仍交给侧栏自己——
接管它，人就再也换不了目的地了。

### Phase 11 · 首页换数据源：音乐 / 流行（已完成）

**问题**：0.10/0.11 的首页前两单是「今日推荐」（排行榜 24 + 最新 12 混拼）和
「音乐排行榜」，两者其实是同一个接口的两种切法——点开哪一单，歌都差不多。
参考的 biu 项目里这两个位置是「音乐」与「流行」，走的是完全不同口径的数据：
一个是**分区推荐流**（有人替你挑），一个是**音乐综合榜**（按曲库热度排）。

**决策**：只换数据源，不动首页结构。侧栏前两项改成「音乐」「流行」，
「最新发布」「正在收听」「收藏」「历史」原样保留。

| 位置 | 原来 | 现在 |
|---|---|---|
| 第一项 | 今日推荐（ranking 24 + newlist 12） | 音乐（`region/feed/rcmd`，`from_region=1003`） |
| 第三项 | 音乐排行榜（`ranking/v2`） | 流行（`music/comprehensive/web/rank`） |

**连带撤掉分节**：Phase 10 的按 `tname` 分节作废——新的两个源都不返回分类字段，
而分节的前提是数据带得动分类。撤掉之后 `TrackListAdapter` 回到单表，
「行上印的序号」与「队列下标」合并回一个数，`submitSections` / `Row.Head` /
`item_section_head.xml` / `sectionHeadPositionOf` 全部删除。

**新接的两条接口**：

| 项 | 音乐 | 流行 |
|---|---|---|
| 路径 | `/x/web-interface/region/feed/rcmd` | `/x/centralization/interface/music/comprehensive/web/rank` |
| 关键参数 | `from_region=1003`、`display_id`（页码）、`request_cnt=15` | `pn=1`、`ps=30` |
| 签名 | WBI（缺 key 时退回明文也能通） | 不需要 |
| 前置 | 需要 `buvid3` | 无 |
| 翻页 | 并行拉 4 页 | 只拉一页 |

**踩到的三个坑**：

1. **`related_archive.cid` 不是视频 cid。** 综合榜的顶层与关联块字段是交叉的：
   正确组合是「`related_archive.bvid` + 顶层 `cid`」，实测 8 首 8 通；
   其余三种组合全部 `-404 啥都木有`。取错的表象不是报错，是播放器一首接一首往下跳。
2. **分区推荐流缺 `buvid3` 返回 `62013「暂时没有更多内容了」`。** 这个码读起来像
   「这个分区没内容」，实际是缺设备指纹。真机 CookieStore 里本来就有 buvid3，
   但 `activateBuvid` 只在探针页调用，所以照样踩了一次。
3. **分区推荐流是混合内容。** 实测 5 页 75 条：38 条超过 20 分钟（乐评合集、专辑开箱、
   饭拍现场），另有新闻号发讣告与时政。因此加两道闸门：时长 30 秒~20 分钟；
   标题与 UP 主的关键词黑名单（开箱 / 乐评 / 盘点 / 教学 / 教程 / 饭拍 / 访谈 /
   直播回放 / reaction / 解读；新闻 / 资讯 / 日报 / 晚报 / 快讯 / 央视 / 新华社）。
   闸门只挡最明确的几类——「翻唱 / 演奏 / MV / Live / 现场」一个都不挡。

**顺带确认的一件事**：`ranking/v2` 在开发机上返回 `-352` 风控，真机同一接口 `HTTP 200`。
代理出口 IP 会污染结论，接口问题一律以真机日志为准。

| 音乐 | 33 首（4 页 60 条过滤后） |

### Phase 12 · 「正在收听」与浏览解耦（已完成）

**问题**：用户问「正在收听和流行为什么是一样的」。

表面看这一问是正常的——它是当前队列的镜像，从「流行」起播，队列就是流行那 28 首，
两页本来就该一样。但真机一验发现不止如此：**只要浏览过一页，队列就被换成那一页**。

**根因**：`playQueue()` 存的是调用方传进来的那个 `List` 本身，而首页传的是
`TrackListAdapter.snapshot`——适配器内部那个 `ArrayList`。适配器换一页的实现是
`clear() + addAll()`，**原地改写同一个对象**，播放器的 `queue` 跟着一起变。
于是「正在收听」永远等于「最后浏览的那一页」，而底栏还挂着上一首：
同一屏上两个控件各说一套，用户看到的就是「为什么这两栏一样」。

**修法**：

| 位置 | 改动 |
|---|---|
| `PlaybackController.playQueue()` | `queue = tracks.toList()`，进来就断开引用 |
| `HomeStage.select()` | 「正在收听」短路到 `playback.queueSnapshot()`，不进缓存也不进协程 |
| `HomeStage.onTrackChanged()` | 比 bvid 序列决定要不要重画，不再比条数 |
| `home_sub_queue` | 「这一轮要听的」→「播放器队列」 |

**为什么缓存也要撤**：`cache` 存的是「上次进来时的队列」，换过歌单就作废。
队列是内存里的实时值，读它零成本，没有缓存的理由。

**为什么比 bvid 不比条数**：自动下一首只换了播的那首、没换队列，重绑会把列表
滚回顶部；而两份恰好都是 28 首的不同歌单，条数又比不出来。

**实测**（小米电视4A，2026-11-01）：

| 项 | 结果 |
|---|---|
| 音乐页播放全部 | 队列 39 首，正在收听 39 首，红条在第 1 行 |
| 转去浏览「我的收藏」（14 首） | 正在收听仍是 39 首音乐——修复前这里会变成 14 首 |
| 从收藏起播 | 队列 14 首，正在收听 14 首，红条在第 2 行、与底栏同曲 |
| 自动下一首 | 列表不滚动，红条跟着走到第 2 行 |
| 冷启动 | 158ms，队列从磁盘恢复，正在收听与底栏同曲 |
| FATAL | 0 条 |

### Phase 13 · 歌词：把 B 站 CC 字幕当歌词（已完成）

**起点是一次调研**：先在 biu 的源码里看它怎么做歌词（`src/components/lyrics/`），
再用两个探针脚本量了 60 条稿件的实际覆盖率（`tools/probe_subtitle.py`、
`probe_subtitle_batch.py`），确认值得做才动手。

**链路**（和 biu 一致，一行没抄，是同一套接口）：

| 步 | 做什么 | 关键点 |
|---|---|---|
| 1 | `x/player/wbi/v2?bvid&cid` | WBI 签名 + **必须登录**；匿名返回 `code=0` 但列表为空 |
| 2 | 取中文那条的 `subtitle_url` | `//aisubtitle.hdslb.com/...` 补 https；公开 CDN，裸 GET |
| 3 | 读 `body[{from, content}]` | `from` 是**秒**（两位小数），不是毫秒 |

**三个真机踩到的坑**：

1. **字幕 URL 只有约 30 秒有效期**（`auth_key` 首段就是过期时间戳，两次实测剩 29 秒）。
   所以只缓存解析后的文本，URL 一次都不留，每次播放重新问一次 player 接口。
2. **匿名请求不报错，只给空列表**。和分区推荐流的 `62013` 是同一类谎报，
   排查时容易往 cid 上想。未登录时干脆不发这次请求。
3. **多 P 合集的 cid 要用顶层 cid**，和 playurl 那个坑同源。

**过滤（三道闸门）**：字幕是整段语音识别，带解说的歌单会把「嗨大家好」一起打出来。
B 站把**唱的**那几行用 ♪ 包起来，说话的不包——这是唯一的过滤依据。

| 闸门 | 判据 | 拦住什么 |
|---|---|---|
| ♪ | 只留被 ♪ 包住的 | 解说词、口播（实测 ♪ 覆盖率 98~100%） |
| 条数 | < 8 行不算 | 只有几句哼唱的视频 |
| 行距 | 平均 < 500ms/行不算 | AI 逐字切碎 |

拦不住的一类：AI 对整张纯音乐专辑「听」出一套假歌词（`How anne` / `那COUPANDA`）。
结构指标和真歌词几乎一样（行距 4.8s vs 5.8s、平均 7.6 字 vs 7.9 字、唯一行 57% vs 61%），
统计上区分不出来；再狠的规则会误杀英文歌。已知问题，接受。

**版式**：歌词和封面**同一块位置切换**，不并排（并排会让封面缩到 160dp 以下、
歌词只剩半屏宽）；`player_main` 高度写死 340dp，因为歌词层是 `match_parent`，
封面层一 GONE，`wrap_content` 就塌成 0。默认显示歌词，没有字幕时无声退回封面。
（这套「同一位置切换」在 Phase 14 被推翻——见下。）

**交互**：下键**短按切播放模式、长按切封面/歌词**。原本想放 MENU，实测小米电视
遥控器的 MENU 长按会直接拉起系统设置面板，抢不过。下键的短按动作本来就低频，
挂长按不挤占东西；短按改成抬手才生效，所以长按不会先连着切两三次模式。

**实测**（小米电视4A，2026-11-01）：

| 项 | 结果 |
|---|---|
| 冷启动首屏 | 156ms，内存 36MB |
| 有字幕的歌 | 《老歌珍藏CD3》583 行、李健《母带精选集》2547 行，滚动与高亮正常 |
| 无字幕的歌 | 「辅酶Q10」字幕 158 行、唱的 0 行 → 丢弃 → 显示封面 |
| 长按下键 | 封面 ⇄ 歌词切换正常，短按仍切模式 |
| 切歌 | 歌词跟着换，晚到的旧结果按 cid 丢掉 |
| FATAL | 0 条 |

**已知限制**：纯音乐合集会出现 AI 幻觉出来的假歌词；切歌后到字幕返回前
（首次播放约 1~3 秒）右栏先空着，是有意为之——宁可短暂空一下，也不要让上一首的
歌词停在新歌的屏幕上。

### Phase 14 · 播放页改左右两栏（已完成）

用户拿汽水音乐桌面版播放页的截图要求照做，并明确「所有封面图改回原来的大小」。

> 0.14.1 把左栏从 340dp 放到 420dp、封面从 224dp 方图改成 400×225dp 的 16:9，
> 见 Phase 15。本节保留当时的过程。

**版式**：左栏 340dp、右栏吃掉剩下的宽（960 − 40×2 − 340 − 40 = 500dp）。

```
左栏 340dp                          右栏 500dp
┌──────────┐
│ 封面 224 │                       每个人受伤的样子
└──────────┘                       本就不会完全一样  ← 当前行 1.14 倍
歌名 24sp 两行            ♡         夜深想起曾经擦肩的人
歌手                              回忆涌上来默默落泪
────────────  进度条
0:07                    341:58
顺序   ⏮  ▶  ⏭   3 / 30
```

**三个决定**：

1. **封面不放小。** 224dp 是 0.9.0 那一版的值。0.13 之所以不并排，是怕封面被挤到
   160dp 以下——实测算下来 340dp 左栏放 224dp 封面还有 58dp 余量，同屏完全成立。
   0.13 那个「同一位置切换」因此撤掉，下键长按也一起撤了（下键回到纯切模式）。
2. **控制键不按屏幕宽度铺开。** 汽水是五键横铺，我们左栏只有 340dp，铺开就散了。
   改成两端放状态（模式 / 第几首）、中间三个动作；两端各固定 52dp，否则「顺序」比
   「3 / 30」窄，播放键会被挤偏一格。
3. **当前行用 scale 放大，不改 textSize。** textSize 会改测量高度，居中的那一行
   自己把行高撑大，滚动位置跟着抖；`scaleX/scaleY` 只在绘制层放大，布局一个像素不动。

**歌词改为每句居中**（原来左对齐）。歌词是一句一行，居中后整块有个竖轴，
读的时候眼睛不用横着找起点；标题那种三十几个字的长句才需要左对齐。

**没有歌词时**右栏不再整块空着，留一行「暂无歌词」（14sp / 45% 透明）——
空着的半屏会被读成「没加载出来」。加载中不写这行字，避免两态混淆
（`lyricLoaded` 区分「没问完」和「确实没有」）。

**实测**（小米电视4A，2026-11-01）：

| 项 | 结果 |
|---|---|
| 冷启动首屏 | 158ms，`TOTAL` 37MB |
| 有字幕 | 李健《母带精选集》、《青花瓷》弹唱，当前行居中放大、上下各 6 行 |
| 无字幕 | 「辅酶Q10」158 行唱的 0 行 → 右栏「暂无歌词」 |
| 上键进进度条 | 白点浮出、左右快进 15 秒（3 次）正常 |
| 下键 | 短按切模式；按住 1.2 秒只切一次（`repeatCount == 0`） |
| 切歌 | 封面、歌词、模式、序号全部跟着换 |
| FATAL | 0 条 |

**残留**：`--:--` 出现在冷启动恢复后的暂停态（没有播放器实例就没有时长），
和 0.13 一样，属已知行为。

### Phase 15 · 封面改回 B 站原图的 16:9（已完成）

用户第二次说「所有封面图改回原来的大小」，并追加一句「去看 bilibili 原封面」。

**根因不是控件尺寸**：播放页 224dp、首页头图 100dp、底栏 42dp，三个值从 0.9.0 起没动过。
真正的问题是**图片被 CDN 裁过**：

```
原图   https://i2.hdslb.com/bfs/archive/<hash>.jpg                       1920×1080（16:9）
过去   ...@480w_480h_1c.webp   1c = 按指定比例裁切 → 只留中间 1080×1080
现在   ...@800w_450h_1c.webp   16:9 原比例，CDN 只缩不放，一个像素不切
```

`FeedApi.reCrop(cover, w, h)` 一直传正方形尺寸，于是同一张 16:9 的实拍封面
（《老歌珍藏》系列是一整间影音室，两侧各一支落地音箱）只剩中间那块，
左右各四分之一被切掉。三个调用点全是方图，从 0.9.0 起就这样，不是 0.14 引入的。

**改法**：高度不动、宽度按 16:9 展开——画面完整，而且不比以前矮。

| 位置 | 过去 | 现在 |
|---|---|---|
| 播放页封面 | 224×224dp | **400×225dp**（左栏 340 → 420dp） |
| 首页头图 | 100×100dp | **178×100dp** |
| 首页底栏 | 42×42dp | **75×42dp** |
| 取图参数 | 480²、300²、96² | 800×450、356×200、150×84（均 2 倍密度） |

**实测**（小米电视4A，2026-11-01）：冷启动首屏 153ms、`TOTAL` 37MB；
《老歌珍藏CD11》封面两侧音箱、器材全部可见；「火力陀螺王」四个人物完整；
切歌时封面跟着换；右栏歌词仍垂直居中；FATAL 0。

**教训**：`1c` 参数是「裁切到指定比例」，不是「缩放到指定尺寸」。请求方图的控件
应该传 16:9 的图，让 `centerCrop` 自己裁——那样也只是显示层裁，原图该给多大给多大；
预先把图裁死，等于把可以再取的信息永久丢掉。

### Phase 16 · 多 P 稿件当合集展开（已完成）

用户反馈：「现在播放的在 bilibili 上是一个合集，我们现在只能显示和播放第一首。
要求能够显示正确的合集名和歌曲名，合集歌曲列表。」

**问题**：音乐区里「一张专辑」最常见的形态就是一个 100 P 的稿件——稿件标题是专辑名，
每个 P 是一首歌。列表接口把它压成**一条**记录下发，只带 P1 的 cid。
照单全收的话，这张专辑在应用里就是一本书只有第一页，按下一首还得跳到别人家去。

**接口**：`x/web-interface/view?bvid=` 一次给全所有 P（`pages[]` 带 cid / part 名 / 时长），
100 P 的响应约 8KB，比逐首打 playurl 便宜得多。

**改动**：

| 层 | 改动 |
|---|---|
| `Track` | 加 `album`（合集名）/ `pages`（P 数）/ `pageNo`（分 P 号） |
| `CollectionApi`（新） | 拉 view → `pages[]` 转 `Track` 列表；内存 LRU 8 张 + 磁盘 40 张、24h 过期；同一 bvid 并发只打一次接口 |
| `PlaybackController` | 起播后把队列换成整张合集（只换队列不重取流，播放头不动）；新增 `playAt(index)`；取流缓存键从 bvid 改成 cid（100 首共用一个 bvid，按 bvid 命中会拿到 P1 的流） |
| `NowPlaying` | 右栏加「歌词 / 曲目」两页签；显示合集名；新增 `PartAdapter` + `item_part.xml` |
| `HomeStage` | 列表行加「合集 N 首」角标（能拿到 P 数才显示，不额外发请求） |
| 正在播标记 | 从 bvid 改成 cid 判定——合集内 100 首共用一个 bvid，按 bvid 标会整列亮起红条 |

**三个坑**：

1. **焦点被系统连发事件冲走**。长按判定生效后，系统为了模拟长按会继续重复发 DOWN
   （先 500ms 后每 33ms 一次）。这些连发事件落进列表，焦点从刚钉住的第 1 行
   一路推到第 7 行。修法：长按生效后剩余的连发一律吞掉。
2. **长按与列表滚动抢同一个键**。曲目表里按住下键本该是「连着往下翻」，
   长按翻页会让列表只能移动一行。修法：焦点在曲目表里时，下键整个归列表；
   从曲目表回歌词页改走「在最上面一行按上」。
3. **不能用列表接口给的 P 数当判断依据**。`videos` 字段只有最新发布和历史给，
   音乐区、综合榜、收藏夹都不给——而合集恰恰大量出现在收藏夹里。
   早先的 `if (track.pages == 1) return` 让这些来源的合集永远展不开。
   修法：判断依据改成实际拉到的 view 结果（`pages` 只当提示）；
   展开的请求量与「用户实际听过的歌数」成正比，不是列表条数——
   `expandCollection` 只在起播与冷启动恢复时调用，浏览列表不会触发。
   CollectionApi 的磁盘缓存把同一 bvid 的查询压到 24 小时一次。

**还有一个坑：cid 为 0 的来源**。收藏夹与搜索的列表接口不给 cid（`cid = 0`），
展开时用 `track.cid` 去分 P 表里找位置永远找不到。修法：cid 为 0 时取第一页
（顶层 cid 就是 P1 的 cid，取流时补出来的也是它）。

**实测**（小米电视4A，2026-11-01）：100 P 合集在列表显示「合集 100 首」角标；
播放页显示合集名《【Hi-Res无损音质】王杰歌曲音乐合集》、歌名为 P 名、计数 1/100；
曲目表焦点钉在正在播那一行；选曲后歌名/计数/红竖条同步；左右键在合集内切歌；
长按下键翻页签；按住下键连翻到第 28 行；第一行按上退回歌词页；
50 P 粤语歌合集（来自收藏夹，cid=0）也能展开成 50 首；
单曲《这次是真玩爽了》正确地不展开、无合集名、计数 6/30；
冷启动后合集角标仍在（走磁盘缓存）；应用侧 FATAL 0、冷启动 159ms。

### Phase 17 · 收藏夹管理、关注与作者主页、指纹化按键（已完成）

这一轮把「歌从哪来」这条线补完整：能建夹删夹、能看关注的人、能从歌手名进到人，
顺手把播放页「一按键就动作」的老毛病改成「点到图标才动」。

**一、收藏夹（建 / 删）**

侧栏「我的收藏」原来只读不写。现在列表底部两个入口：新建、删除。

- 建夹：自绘键盘输名字 → `POST x/v3/fav/folder/add`。键盘不许用系统 IME——
  第三方桌面会把输入法裁掉，屏幕上只剩一个空框。
- 删夹：**两步确认**，第一次确认把这行文案换成「再按一次确认删除《名字》」，
  焦点不许动。默认收藏夹不可删（接口会报，不如直接不给点）。
- 删夹参数是 `media_ids`（**复数**、逗号分隔），单个夹也要传成列表。

踩过的坑：第一次确认后焦点被洗到「取消」按钮，第二次确认打在了错的行上。
两个原因叠在一起——`notifyDataSetChanged()` 整表重绑洗掉焦点；
`list.post` 时 RecyclerView 还没布局完，拿不到 holder，焦点落到唯一抢得到的按钮。
修法：`refreshOne(id)` 局部刷新 + `post` 两次再钉回原行；重载列表前先记下
`focusedPosition()`，重载后停在原位。

**二、播放页改成「点图标才动」**

原来左右键直接切上一首/下一首、确认键在页面任意处都是暂停。问题不是「不好用」，
是**误触代价太高**：想停一下歌，手指蹭到左键就换歌了。

现在全部挂 `OnClickListener`：上一首 / 下一首 / 播放暂停 / 收藏 / 播放模式。
方向键在播放页只做一件事——移动焦点。

实测：`player_mode` 连点三次「顺序 → 单曲 → 随机 → 顺序」；`player_fav`
点两次分别打出 `收藏写入 HTTP 200` / `云端取消收藏（移出 1 个夹）`。

**三、「我的」面板显示头像**

`panel_account.xml` 加 `account_face`，登录后按 `nav.face` 加载。
拿不到头像时整块收起来——一个空圆比「未登录」三个字更像缺图。

**四、关注列表 → 作者主页**

- 侧栏新增与「我的收藏」同级的「关注」（`x/relation/followings`，实测 26 人）。
- 点人进作者主页（`overlay_space`）：头像 / 昵称 / 签名 / 等级 / 关注按钮 + 投稿列表
  （`x/space/wbi/acc/info` + `x/space/wbi/arc/search`）。
- 关注按钮走 `POST x/relation/modify`，双向实测都是 HTTP 200。
- 投稿行：点行起播，点右侧的心收藏（同样落云端）。

**五、歌手列可聚焦**

列表行的「歌手」原来只是文字。现在光标右移能落到歌手列，确认即进该作者主页。
行内横向由 `TrackListAdapter.SongHolder.moveHorizontal / whichColumn` 接管，
**不写 XML 的 `nextFocusRight`**：item 上只要设了 `nextFocus*`，FocusFinder 就不用
几何搜索找下一行了，RecyclerView 的纵向滚动整个停摆。

**六、底栏封面上的小播放键**

暂停时按它 = 出声并进播放页；正在放时按它 = 停，留在首页。
两种情况分成两个结果，是因为「我想听」和「我嫌吵」是两种不同的意图。

**这一轮真正的难点不是功能，是 RecyclerView 的纵向焦点。**

首页列表 35 首只显示 6 行，按第 7 次下键焦点纹丝不动。查下来是三件事叠在一起：

1. RecyclerView 只创建可见范围内的行，下一行还没创建时焦点搜索扑空；
2. `LinearLayoutManager.onFocusSearchFailed` 会 `fill()` 补出那一行并 `requestFocus()`，
   但补出来的行坐标在**列表底边外面**（实测 `0,559-655`，列表高 559）——
   焦点移过去了用户看不见，看起来就是光标凭空消失；
3. 底栏贴在列表正下方，全树焦点搜索找「下面」时底栏比补出来的那行更近，
   焦点直接跳到底栏，中间一屏歌被整个跳过。

第一版自管纵向翻行时用了 `RecyclerView.scrollBy(0, ±行高)`，日志显示 `from` 一路从 0 涨到 7，
看上去「修好了」。后来发现 `from` 涨的是 `pending` 的记账，列表**根本没有滚动**：

```
翻行 to=6 h=96 可见 0..5 → 0..5 holder=false focus=null
```

`visibleRange()` 在滚动前后完全一样。改成 `scrollToPositionWithOffset` 之后才真的推得动。
第二次又出了个反向的错——把目标行摆到「来源行原来的位置」，而来源行永远贴顶，
于是每按一次都在把目标行顶到第一行：光标一动不动，内容自己在后面滚。
最终逻辑是「目标行还看得见就一点都不滚，出了可见区才滚到刚好露出来」。

修的过程中还炸出一个崩溃：作者主页的投稿列表按上键必崩，

```
IllegalArgumentException: parameter must be a descendant of this view
  at ViewGroup.offsetRectBetweenParentAndChild
  at FocusFinder.findNextFocus
```

原因是在 `onFocusSearchFailed` 里**同步**滚了列表：RecyclerView 立刻回收、搬移子 view，
而 FocusFinder 的调用栈还捏着原来那个 view。滚动一律推迟到 `post`，并且只记 position 不记 view。

**实测**（小米电视4A，2026-11-01）：
建夹 `test` → HTTP 200 → 删夹两步确认 → HTTP 200、列表里消失、焦点不动；
首页列表连按 8 次下键到第 9 首、连按 8 次上键回到第 1 首；键盘 `q→w→e→r→t`、
`t ↓ g`（按字母列号对齐）；「我的」面板头像与昵称正常；关注列表 26 人 →
点第一人进作者主页 → UP 资料 200 / 投稿 30 条 → 关注 ↔ 取关均 HTTP 200 →
投稿行收藏 ↔ 取消失败均 HTTP 200 且焦点稳定；底栏小播放键暂停→播放+进播放页、
播放中→暂停+留在首页；搜索页键盘回归正常；应用侧 FATAL 0。

### 补丁 0.16.3 · 三处「按下去没反应」

真机上补测出的三个问题，共同点都是**按键被吞掉、屏幕上没有任何反馈**——
用户无法判断是「没点到」还是「坏了」。

**一、「正在收听」里点歌手，有的行不响应**

队列是播放器的镜像，里面混着不同来源的条目。收藏夹那一路（`fav/resource`）只给作者名字、
不给 mid，`ownerMid` 就是 0；原代码在 `ownerMid > 0` 才进主页，否则只把焦点停在那一行。
实测点《1. 飄移》打出的就是 `mid=0`。

修法：缺 mid 时拿 bvid 反查一次 `x/web-interface/view` 补上（`MainActivity.openArtistOf`）。
**不用作者名字搜人**——同名 UP 主太多，搜到的那位多半不是这一行的人。
实测 `mid=0 → 反查 UP：音乐可滴答 bvid=BV1bUHH6vECg → mid=211515019 → UP 资料 200`。

**二、换单之后光标悬空**

「播放全部」按钮上写着 `android:nextFocusDown="@id/home_fav_new"`，而「新建收藏夹」只在
「我的收藏」这一单里存在。在「正在收听」页按确认，焦点会落进一个 GONE 的控件：
屏幕上一点高亮都没有，之后每个方向键都像按在空处——表现就是「遥控器失灵」。

修法分两步：

1. 删掉那条 `nextFocusDown`，把「列表顶行 ⇄ 播放全部 ⇄ 收藏夹工具条」这三格写进
   `HomeStage.handleKey`。删掉之后几何搜索会把「播放全部」整个跳过（实测从侧栏右键
   直接落到列表第一行），所以必须自己接，不能只是删。
2. `render()` 末尾加 `rescueFocusIfLost()`：焦点 `isShown == false` 但
   `isAttachedToWindow == true`，就说明它藏在一个 GONE 的容器里，交回侧栏当前这一项。
   只判 `isShown` 不够——列表刚换数据时那一行也被回收、也不可见，但它已经离树，不用管。

**三、播放页打开时光标落在进度条上**

`openPlayer()` 里 `playerOverlay.visibility = VISIBLE` 之后立刻 `requestFocus()`，
这一刻还没测量布局，请求失败，焦点被系统塞给第一个抢得到的控件——实测是 `player_seek`。

修法：`focusPlay()` 里 `post` 一帧再聚焦 `player_play`。
用户打开播放页第一眼要能按下去的就是「播 / 停」，不是一条只能左右拖的滑杆。

**实测**：「正在收听」第 1 行点歌手 → `UP 资料 200` / 投稿 10 条；
收藏来源那行 → `mid=0` → 反查 200 → 主页打开；
收藏页 `列表顶行 ↑ 播放全部 → 新建收藏夹 → 列表顶行` 闭环；
「正在收听」页 `列表顶行 ↑ 播放全部 ↑ 侧栏`；
播放页打开焦点在 `player_play`，按确认即暂停；应用侧 FATAL 0。

### Phase 18 · 品牌与侧栏图标（0.17.0，已完成）

四件事：给应用一个中文名、把 K 标重描一遍、主界面左上角立起来、侧栏每项前面加图标。

**一、名字**

`@string/app_name` 从 `KunPlayer` 改成 `B站音乐TV版`。桌面图标下的名字、侧栏品牌位、
系统设置里的应用名都读这一条，改一处三处同步。`KunPlayer` 只留在仓库名、包名和
日志前缀里，界面上不再出现。

**二、K 标重描**

旧 `banner.png` 里那个 K 只有 320×180、还是位图，放大就糊。做法不是「照着画个像的」，
而是**按像素量的**：竖笔占 x65..x89（宽 25）、高 112；白色上斜与橙色下撇的水平厚度都是 27；
两笔交汇在 `(122, 90)`，正好是竖笔中线。取样色：白 `#F2F5F7`、橙 `#FF8A3D`、底 `#0E1215`。

重描时踩到一个坑：按平行四边形算，两笔的左下顶点收在 `x=30`，而竖笔右边在 `25.4`——
中间 4.6 个单位会露出一条背景色的斜缝。原图里 K 的两笔是长在竖笔上的，左端必须压到
竖笔右边（`25.4`）。三处（矢量 / 横幅 / 图标）用同一个几何，改一处要三处一起改。

**三、左上角品牌位**

侧栏顶部原来是 `app_name` 一个 TextView。现在换成「矢量 K（20dp 高）+ 中文名（15sp）」的
横排。名字用文本而不是画进图里：能跟着系统字号变、能被读屏念出来、换语言不用重做图。

**四、侧栏图标**

九项各一个 18dp 线性图标（`ic_nav_*.xml`，24 viewport、1.8 描边、圆头，和 `ic_heart` 同一套笔法），
`drawablePadding` 14dp——正好是 14sp 字号下一个汉字宽，即「隔一个字符」。

图标着色不用 `tint` 选择器，在 `paintNav()` 与聚焦回调里显式 `setTint`：
选中或光标停着是 `text_primary`，其余 `text_secondary`。每个 item 的 drawable 都要
`mutate()` 出独立副本，不然给「音乐」刷白会把九项一起刷白。

「流行」原本画的是火焰（外焰 + 内焰）。18dp 上渲染出来就是一颗水滴——火焰的辨识度
全靠顶上那道 S 弯和内焰，这两样在 36 个像素里留不住。改成上扬折线 + 箭头，
同样尺寸第一眼就能读出来，而且「热门」本来就等于「趋势往上」。
调图标时用无头 Edge 把 vector 的 pathData 抠出来拼成 HTML 一次看九个小样，
比每改一版就装一次包快得多。

「我的收藏」单独建了 `ic_nav_fav.xml`（`ic_heart` 缩到 90%）：那颗心的路径几乎铺满 24 格，
九项并排时只有它看着比旁人大一号。播放页的收藏按钮仍用 `ic_heart` 原尺寸。

**实测**（小米电视4A）：桌面卡片显示「K + B站音乐TV版」，卡片下方 label 同名；
侧栏九个图标逐项可辨、大小一致；连按五次下键，焦点从「音乐」走到「关注」，
高亮胶囊与图标变白同步；切页后选中项图标为白、其余为灰；应用侧 FATAL 0。

### 补丁 0.17.1 · 「我的」页脚加应用名与版本号

自用 sideload 包最常问的一句是「电视上装的是哪一版」，以前只能进系统设置翻。
现在「我的」页右下角一行小字：`B站音乐TV版 0.17.1-about (24)`。

**位置**：页脚，不进中间那一列。中间的「头像 → 昵称 → 按钮」是一条读下来的，
末尾再接一行灰字会把这条链拽长；版本号也不是账号信息，它和页面主体没关系。

**取数**：`BuildConfig.VERSION_NAME / VERSION_CODE`，与 `Crash.kt` 的崩溃头、
`Diag.kt` 的启动行同源。三条路径各取一次会漂移——屏幕显示 0.17.1 而日志写 0.17.0
这种事，只有在真出问题时才发现，那时最不该怀疑的就是版本号。

**结构**：`panel_account.xml` 根由 `LinearLayout` 换成 `FrameLayout`，
中间那段仍 `gravity=center`，页脚 `layout_gravity="bottom|center_horizontal"`。
版本行不可聚焦——这一页只有一个焦点位（登录 / 退出），多一个焦点位就得多一次方向键。

**实测**：桌面启动 → 侧栏连按八次下键到「我的」→ 确认 → 页脚显示
`B站音乐TV版 0.17.1-about (24)`；返回后焦点先回侧栏当前项，按键通畅；应用侧 FATAL 0。

### 补丁 0.17.2 · 歌词「有却不显示」

报障原话：「现在在播放的有歌词为什么没显示」。诊断不靠猜：把设备上的
`shared_prefs/player.xml` 拉下来解开队列，再用 PC 端带 Cookie 直连接口逐条核对。

**断点一：`cid = 0` 把整条链路短路。**

`FavApi` / `SearchApi` 构造条目时写死 `cid = 0`；`PlaybackController.resolve` 取流时
按 bvid 反查过 cid，但**没有写回队列**。歌词这边 `loadLyrics` 的守卫是
`if (track.cid == lyricCid) return`，而 `lyricCid` 初值也是 0 —— 第一首收藏的歌一进来
就判成「同一首」，请求不发、`lyricLoaded` 仍是 false，`paintRight()` 于是两样都不显示：
右栏一片空白，连「暂无歌词」都不写。**空白和「暂无歌词」是两条不同的故障分支**，
看到空白就该想到「根本没问」，不要先去查接口。

修法：守卫改成 `track.cid > 0 && track.cid == lyricCid`；
`LyricsApi.load` 缺 cid 时用 `x/web-interface/view` 按 bvid 反查（与作者主页同一套兜底）。

**断点二：拿 ♪ 去筛人工字幕。**

♪ 是 AI 字幕用来把「唱的」和「说的」分开的记号；人工上传的字幕（`lan=zh-Hans`）
整份都没有这个记号。实测《阳光彩虹小白马》`BV1RdZEY8E8T`：41 行、**0 个 ♪**、
均隔 2153ms —— 这是一份标准的歌词字幕，旧规则整份丢掉。

修法：按 `lan` 分流。`ai-*` 维持 ♪ 过滤 + `MIN_SUNG = 8`；人工字幕整份采用，
下限 `MIN_HUMAN = 4`。行距闸门（均隔 ≥ 500ms/行）两种都保留，它拦的是逐字切碎的误识别。
缓存读取的条数下限同步放开到 `MIN_HUMAN`，否则新判据写进去、读回来又被旧下限砍掉。

**实测（小米电视4A）**：收藏第 2 首《张信哲母带精选集》→ 日志
`cid 缺失，按 bvid 反查 BV1HJni6ZEWL` → `字幕 1001 行（原 1002 · ai-zh）` →
播放页右栏滚动歌词正常、当前行高亮；缓存落盘 `files/lyrics/42911205922.txt` 1000 行。
另核查 4 条收藏 + 14 条音乐区排行 + 12 条最新：无字幕 12 条，有字幕的按新规则全部可用。

**遗留**：`x/player/wbi/v2` 只认 cid，多 P 稿件缺 cid 时反查拿到的是第 1 P 的 cid。
取流走的是同一条路，两边一致，所以不会错位；但如果哪天要按「第 23 首」取字幕，
得改成用 `x/player/pagelist` 按 `pageNo` 取，view 做不到。

### 补丁 0.17.3 · 字幕的两条取数通路与五种空态

报障原话：「现在播放的也没有歌词」。这次先把**「这首到底有没有字幕」**当成独立问题查，
再决定改哪一层。取现场三步：截播放页 → 拉 `files/diag.log` → 用 PC 端带 Cookie
按同一个 bvid/cid 直连接口对照。

**一、报障的那首，内容侧确实没有。**

《【田馥甄】6张专辑全、后台播放…》`BV1sF4c6jEWf` 是 8 个分 P 的整轨专辑，
P1 时长 2368 秒（39:28），与播放页 39:27 对得上——**cid 没取错**。
逐 P 查 `x/player/v2`：P3/P4/P6/P7 全空，P1/P2/P5/P8 时有时无一条 `ai-zh`。
把 P1 那条下载解开：214 行、**0 个 ♪**，内容是「大蚂蝗每个人都爱吃 / 但你们了解蚂蝗吗 / …」
——**别的科普视频的字幕串过来了**。这类整张专辑整轨、7 小时合集，
本来就没有逐句歌词可显示，判据把这份脏数据丢掉是对的。

**二、`wbi/v2` 与明文 `player/v2` 的字幕集合不同。**

同一个 cid 同时问两个接口：

| 调用 | code | subtitles |
|---|---|---|
| `x/player/wbi/v2?bvid=&cid=`（无签名） | 0 / OK | **0 条** |
| `x/player/v2?bvid=&cid=`（明文） | 0 / OK | **1 条 ai-zh** |

两条路不是互斥的降级关系，看到的是不同的字幕集合（AI 字幕按需生成，有生成窗口）。
原来只问签名接口，于是一批「其实有字幕」的歌也被判成没有。
修法：签名接口为空时再问一次明文，两边都空才认定没有；**只要有一个接口明确回了空列表，
就按「没有字幕」处理，两个都请求失败才算网络故障**——否则网络一抖，文案会错报成
「B 站没提供字幕」。

**三、空态必须说清是哪一种。**

原来五种情况共用一个「暂无歌词」：内容没有、字幕是解说、网络失败、未登录、拿不到 cid。
用户只能反复问「为什么没有」。现在 `LyricsApi.load` 返回 `Outcome.Ok/No(Why)`，
`Why` 四档映射到四句话，未登录单独一条：

| Why | 右栏文案 |
|---|---|
| `NO_SUBTITLE` | B 站没有为这首歌提供字幕 |
| `NOT_LYRIC` | 字幕内容不像是歌词，已隐藏 |
| `NETWORK` | 歌词加载失败 |
| `NO_CID` | 暂无歌词 |
| 未登录（不进 `load`） | 登录后显示歌词 |

**实测（小米电视4A）**：

- 田馥甄 P1 →「B 站没有为这首歌提供字幕」（两个接口都空）
- 王杰 100 首合集 → `wbi 空，明文接口拿到 1 条` → `字幕 6 行（lan=ai-zh），可用 0 行，丢弃`
  →「字幕内容不像是歌词，已隐藏」
- 张信哲母带精选 → 右栏《过火》正常滚动，当前行高亮（回归未受影响）
- 应用侧 FATAL 0

**方法记录**：`NO_SUBTITLE` 分支一度没打日志，日志里只剩旧版本的「这首歌没有字幕」，
差点误判成「新代码没跑」。凡是返回给用户的结论，都要在日志里留一行——空态文案是
给用户看的，日志是给自己看的，两者不能只留一个。

### 补丁 0.18.0 · 播放页的三处光学问题

需求原话：「帮我美化播放页」。选定方向后又补了三条：封面精致些、歌词上下压缩、
播放键太大。三件事看着是审美，逐条量下去全是**参数写错了**。

**一、背景的模糊封面从来没画出来过。**

`player_bg` 的 `alpha=0.1`，`now_scrim` 又盖了一层 82~85% 的底色。两层叠乘之后
封面只剩 1% 的贡献——任何一张封面最后都收成同一块 `#17171A`。所以这页的背景
不是「选得低调」，是**根本没有背景**。

改成 `alpha=0.75` + 横向渐变遮罩（左 `#EB17171A` 92% → 右 `#99171A1E` 60%）。
左半边压得住，因为歌名、时间、控制键都在左边；右半边留给封面的颜色。实测红封面的歌
整屏泛红、蓝封面整屏泛蓝，不用看标题就知道换没换歌。

**二、深底上做不出投影，只能做受光的边。**

想给封面「浮起来」的第一反应是 elevation / 阴影。在 `#17171A` 上行不通：
黑影叠黑底没有对比度，加完只会让图看起来发灰。深色界面里的层次只有一种来源——
**边的亮度**。于是：

| 部件 | 做法 |
|---|---|
| 圆角 | 8dp → 14dp（8dp 在 400×225 上几乎没有弧度，像贴纸撕了个角） |
| 描边 | 2dp `#33FFFFFF`，外半边被 `clipToOutline` 裁掉，实际剩 1dp |
| 顶沿 | 22dp 高、`#33FFFFFF → 透明` 的渐变，读作「受光的斜面」 |
| 焦点 | 描边提到 `#99FFFFFF` + 整块放大 2% |

焦点那一条是重点：原代码用 `scale 1.0 ↔ 0.985` 表示封面聚焦，564px 宽的框两端
各动 4px——三米外没人看得出光标在哪。**焦点必须能被看到，不能靠察觉。**

**三、歌词的透明度不分远近，等于没有落点。**

`LyricsView` 原来把所有非当前行一律压到 `0.55`：隔一行和隔八行一样亮，满屏字幕
没有一个视觉中心。现在按距离分级：

| 距当前行 | 0 | 1 | 2 | 3 | ≥4 |
|---|---|---|---|---|---|
| alpha | 1.0 | 0.62 | 0.42 | 0.28 | 0.16 |

分级之后屏幕边缘那几行自己就沉下去了，**因此不需要再叠一层渐隐遮罩**——
遮罩压在高斯模糊的背景上会露出一条直边，比不做还难看。这是「用透明度做渐隐」
而不是「用蒙版做渐隐」的原因。

配套：歌词区上下各收 56dp（原来从 y=0 打满，第一句贴着屏幕上沿，overscan 还会再切一刀），
行内 padding 7→5dp。收进来之后当前行仍在屏幕正中（上下等距），只是边缘退进了安全区。

注意：换行时改成了 `notifyItemRangeChanged(0, size)` 而不是只刷新旧的两行。
透明度依赖「距离」，原来在下一行那句要从 0.16 变成 0.62，只刷两行会把它留在旧色上。

**四、顺手修的四条。**

- 进度条 3dp → 4dp；thumb 10dp **常显**（原来 `alpha=0`，只在聚焦时冒出来，
  等于「进度」这件事平时没有指针），聚焦时放大到 1.5 倍。
- 已播时间用 `text_primary`、总时长用 `text_secondary`：前者回答「听到哪儿了」，
  后者只是刻度，同色会让刻度抢读。
- 播放键 56 → 44dp。白底圆在这一页是唯一的实心块，尺寸一大就把封面压成配角。
- 进度条下加「下一首 · xxx」。**只在顺序模式画**：单曲循环的下一首就是它自己，
  随机的下一首在按下去之前不存在——没有的东西不画，这条沿用 `overlay_now.xml`
  开头那三条老规矩。

**实测（小米电视4A）**：

- 红色封面（《绝区零》EP）整屏泛红；蓝色封面泛蓝，切换立刻可辨
- 封面聚焦：裁出左上角放大对比，白边由几乎看不见变为清晰的亮线（逐像素对比确认）
- 焦点顺序 播放键 → 进度条 → 收藏 → 封面 全部有可见反馈，且第 4 次上键停在封面、
  不会漏到 overlay 后面的首页侧栏
- 歌词 41 行那首：当前行白+粗+1.14 倍，上下四行分四级淡出，首行距屏幕上沿约 75dp
- 切到单曲模式，「下一首」整行消失
- 应用侧 FATAL 0，`files/crashes` 无新增

### 补丁 0.19.0 · 玻璃叠层（歌名骑在封面上）

0.18.0 修的是「光和层次」，这一版修的是**左栏在讲几件事**。原来左栏从上到下是
「一张图 · 歌名 · 歌手 · 合集名 · 进度 · 时间 · 下一首 · 一排键」八段，眼睛要上下跳
八个来回；把歌名歌手搬到图上之后只剩两段：一张有字的图，一排键。

**一、五层压在 420×236 上。**

```
图（centerCrop）
底部压深  148dp，顶边全透 → 中点 70% → 底边 98%
顶沿受光  22dp，20% 白
歌名 23sp / 歌手 14sp，左右 18dp、底 16dp
亮边 1dp
```

压深是白字骑图的代价，量了两轮：第一版停在 65%，真机上放到浅色封面（白发少女那张）
后面，40% 的灰压在浅色图上还是一块浅灰，14sp 的歌手名直接糊进去。现在改成
「上疏下密」——两行歌名的最上一行落在 78% 附近，字的脚下必须是实的。
**同时去掉了文字阴影**：阴影会在笔画边缘糊出一圈毛边，浅色封面压深之后反而更脏，
可读性交给渐变就够。

**二、`bg_album.xml` 的圆角从 8dp 变成 14dp 也没用——它只是给 `clipToOutline`
提供一个轮廓。** 真正决定「浮起来」的是那道亮边，圆角只负责不让边出现锯齿。

**三、焦点反馈：提亮卡边这条路走不通。**

原来聚焦时把卡上那道描边从 20% 提到 60%。听上去对，实际不行：描边是**画在图上面**的，
浅色封面（白底海报、亮蓝天、粉色 MV 剧照）本身比它亮，提亮等于没提。真机上拿
周深那张粉色封面逐像素比过——聚焦前后边缘只差 3 个色阶，等于没有反馈。

换成卡外一道环：2dp、`#99FFFFFF`、圆角 24dp、离卡 10dp。它浮在页面底色上，
跟封面什么颜色无关，任何一张图都成立。卡同时放大 2%，所以间隙必须给 10dp——
按 8dp 做的时候放大后只剩 4dp，环几乎贴在卡上，看起来像双线框。卡上的常驻亮边
在聚焦时不再跟着提亮：有环再提亮就是框里还有框。

**四、收藏心上移进封面右上角，垫一层半透黑圆。** 白心放在浅色封面上会消失，
垫底之后任何封面都成立。它仍在封面之后可达，但封面卡的 `nextFocusDown` 直接给
进度条——下键从封面进这里会绕一圈。

**五、播放键从实白圆改成 20% 半透明白。** 玻璃版里封面是唯一的重心；一块实心白圆
体积不大，但它是纯白，会把视线从图里拉出来，整页出现第二个视觉中心。半透明白
还看得出是按钮，焦点态加 2dp 亮边并提到 30%——半透明块只调透明度变化不明显，
得有一条能一眼看到的边。

**实测（小米电视4A，0.19.0 / 28）**：

- 歌名《全球披头士日快乐！》骑在图上清楚锐利，放大看没有阴影毛边
- 封面聚焦时环完整闭合、四边都在、间隙均匀，不像双线框
- 进度条聚焦有淡色圆角底板、圆点放大；收藏心聚焦有白环
- 空态（没有歌）封面卡整块收起，换成同位置的一段字，起播不跳
- 应用侧 FATAL 0，`files/crashes` 无新增

**踩坑记录**：`adb` 在这个环境里每次命令之间 daemon 会被回收，`connect` 必须在
同一条命令里做，否则 `device not found`。截图是 1920×1080，`ViewImage` 显示时
缩到 1080×608——裁剪坐标要按 1920 算，按显示尺寸算会裁到别的地方。

### 补丁 0.20.0 · 「第几首」换成「哪几首」

需求五条，原话：「序号/总数量改成播放列表图标，多P合集同样处理，点击打开列表，
列表在歌词区域打开，打开列表时不显示歌词」「随机/顺序/单曲换成图标」
「封面歌曲名小一点」「收藏按钮移到封面右下角与歌曲名对齐」「光标可以移动到歌手，
点击打开歌手主页关注」。

**一、右栏的主人是「正在听的那一串」，不是「歌词/曲目」两页。**

原来右栏顶部挂着一对页签（歌词 / 曲目），只在多 P 合集时出现。页签要常驻一整行高度，
换来的只是两个词；而「第几首」这件事，一颗图标加一个列表就能说完，还顺带把换歌做了。

于是：`2 / 45` 那颗数字换成播放列表图标，点开右栏换成列表，抬头「播放列表 · 共 N 首」
加一个收起的叉；收起时歌词原样回来。**同一个位置只站一个东西**——两块同时在屏上，
等于把这一页唯一的阅读区劈成两半。

列表里放什么，由来源决定：

| 来源 | 列表内容 | 点一行 |
|---|---|---|
| 多 P 合集 | `album.parts`（分 P） | `playAt` / `playQueue(parts, i)` |
| 其余 | `playback.queueSnapshot()` | `playAt(i)` |

这两件本来就是同一件事——从合集里起播时，队列就是那些曲目。分两个入口反而会问出
「我现在看的是哪个列表」这种没人答得上的问题。

**二、光标不能悬空，这是这一层的通用问题。**

列表一 `GONE`，停在里面的焦点就没了，之后按什么键都没有反应。所以三条路
（图标再点一次、抬头的叉、返回键）都必须把焦点交回打开它的那颗图标。
返回键也改成分级：列表开着先收列表，再按一次才退出播放页——一次返回只退一层。

上键在列表第一行时交给页面，走到抬头的叉上（列表自己走不动了）；在叉上按下键回到
当前行，否则焦点会跑到左栏，人还没看列表就被带走了。

**三、高亮认法要两级。**

`PartAdapter` 原来只按 cid 认「正在播的那一行」。换成队列之后，收藏夹和搜索结果给的
cid 是 0，`0 == 0` 会把每一行都画成正在播。改成：有 cid 按 cid（一百个 P 共用同一个
bvid，只有 cid 分得开），没有 cid 退回队列下标。

**四、三个模式图标。**

| 模式 | 图形 | 为什么 |
|---|---|---|
| 顺序 | 两条首尾相接的箭头 | 「放完这首接下一首」 |
| 单曲 | 同一个环，中间一个 1 | 只改中间那一笔，三米外只比「中间有没有东西」 |
| 随机 | 两条交叉箭头 | 「打散的列表」是乱序排列，不是随机播放 |

三个都用实心，跟同一排的前进/后退/播放键一个手感——那一排全是实心块，
混一个 1.8 描边进去会显得轻一档。单曲里那个「1」按 Material 原版做小了一号，
22dp 下几乎看不见，重画成 7.2 单位高、笔画加粗才立得住（先渲小样比过两版）。
模式名没有丢：换档时仍然有一次飘字提示，`contentDescription` 也留着。

**五、收藏挪到歌名末尾，歌手名可以聚焦。**

收藏原来浮在封面右上角。右上角是「关于这张图」的位置，收藏是「关于这首歌」的动作，
所以挪到歌名那一行的末尾，用 `bottom` 对齐——两行歌名时它跟最后一行齐底，
不会飘在两行中间。

歌手名从「纯展示」变成「入口」：可以聚焦，按确认打开作者主页，到那儿关注。
焦点态是提亮 + 下划线，不加底板：那块字本来就躺在压深渐变上，再加半透明底就是三道边。

**六、作者主页的层级问题。**

`activity_main.xml` 里 `overlay_now` 在 `overlay_space` 之后（更靠上），因为作者主页
是播放页的来处。从播放页点歌手进去时，得把主页 `bringToFront()` 盖上去、按键路由给它，
返回时再 `playerOverlay.bringToFront()` 退回播放页——不然点下去屏幕上什么都不变，
底下的音乐却还在放。

**实测（小米电视4A，0.20.0 / 29）**：

- 开列表：焦点落在正在播那一行，红竖条 + 高亮；抬头「共 36 首」
- 点另一首：直接换歌，红条跟着走，列表不关；日志「列表焦点 → 第 2 行，成功=true」
- 多 P 合集（2 P 的 MV）：列表显示两个分 P，切 P 正常，合集名照旧在卡下
- 返回键：先收列表、歌词回来、焦点落到列表图标；再按一次才退出播放页
- 上键到顶 → 抬头的叉有高亮底框；下键回到当前行
- 歌手名聚焦有白色下划线；确认打开作者主页；返回退回播放页
- 应用侧 FATAL 0（`files/crashes` 里 21:35 那两份是这一版自己踩的 id 冲突，已修）

**坑**：`player_list` 同时给了控制行那颗图标和右栏的 `RecyclerView`，`findViewById`
拿到的是先声明的那个 —— 启动即 `ClassCastException: ImageView cannot be cast to RecyclerView`。

### 补丁 0.21.0 · 字从封面上搬下来

0.19.0 让歌名骑在封面下沿，是为了让左栏只讲两件事。代价是那四样东西
（歌名、歌手、收藏、合集）挤在同一条 148dp 的压深带上，谁都不够呼吸。
这一版反过来做：**字整块搬出封面**，封面只负责交代「这是哪首歌的图」。

参考的是云音乐播放页：方封面居中、歌名与收藏同排在图下面、细进度条、
最后一排里播放键做成胶囊。

**方封面没做成，尺寸改回来了。** 参考图是方的，第一版按 224×224 做了方卡。
但 B 站的稿件封面是 1920×1080 的横图，装进方框要裁掉两侧各四分之一——
实拍封面里两侧的音箱整个消失，只剩中间一块。这笔账比「跟参考图一致」贵，
所以封面恢复 420×236 横卡，只改它下面的排法。

**然后又缩到 3/4（315×177），左栏跟着从 420 收到 360。** 这两件事必须一起做：

- 只缩封面不缩栏，420 的栏里 315 的图左右各剩 52dp。真机上拍下来，封面和它下面
  那四行字各走各的，左栏读起来是「一张飘着的图 + 一堆散落的元素」，不是一块。
- 把文字也缩进到 316 试过：字和进度条、控制行的左缘又差了 104dp，上半缩进下半通栏，
  更难看。控制行也不能缩——40×4 + 84 + 24 = 268 挤进 316，两端状态和中间动作
  之间只剩 24dp，分组感没了。
- 收到 360 之后，315 居中、左右各 22dp，所有元素同宽同左缘。右栏多出 60dp，
  歌词一行能多放三四个字。

配比跟着重算：圆角 14 → 12dp（14 按比例是 10.5，取 12 因为再小切不出圆角）、
顶沿受光 22 → 18dp。**亮边 2dp 不动**——描边外半被 `clipToOutline` 裁掉，
2dp 进去剩 1dp；1.5dp 只剩 1.5 个像素，聚焦缩放一动就闪。常驻的边宁可略重，
不能在动的时候断。

**改了什么**

| 位置 | 原来 | 现在 | 为什么 |
|---|---|---|---|
| 封面 | 420×236，满栏 | 315×177 居中，左栏 360 | 四分之三大小；栏宽跟着收，图才算在栏里 |
| 歌名 | 19sp 骑在封面下沿 | 19sp 独占一行，图下 24dp | 字的脚下不再是渐变带，是页面底色 |
| 收藏 | 34dp，歌名行末，垫半透黑圆 | 44dp，整行右端，无底 | 不再压照片，不需要那层黑；放大到能当动作键 |
| 歌手 | 单独一行 | 与合集名同行，wrap / weight 1 | 单占一行多 20dp，左栏已经贴到下沿 |
| 播放键 | 44dp 圆 | 84×44 胶囊，圆角 22 | 圆在三颗动作键里读作「又一个图标」 |
| 下一首预告 | GONE / VISIBLE | 16dp 固定高，INVISIBLE 占位 | 一出现就把控制行顶下去 20dp，换歌时整排键跳一次 |
| 按键说明 | 左下 | 右下 | 左栏从 425 长到 459，左下没位置了 |

**四条不是「好看」而是「能读」的判断**

1. **封面和歌名不能同宽居中就对**。中间试过把左栏内容缩进 40dp（排版宽 340），
   让封面 260 居中、歌名 340 左对齐，两者只差 40dp。看着是整齐了，
   但横卡一回来就不成立：420 宽的图本来就跟 420 宽的字同宽，缩进是自找的。
2. **播放键必须是这一排唯一的重心**。胶囊一拉长，左右两颗圆图标自动退成卫星；
   保持全圆时五颗键是平的，眼睛找不到该按哪一颗。
3. **爱心不能兼职表示焦点**。它已经用空心/实心说「收藏了没有」，再让它靠颜色说
   「现在选中了」，两件事就会打架。焦点交给白圆底 + 放大 1.08。
4. **合集名跟着歌手走**。B 站的合集名动辄「【Hi-Res无损音质】王杰歌曲音乐合集」，
   给它 weight 1 吃掉剩下的宽度、超长自己省略；歌手 wrap_content 且 maxWidth 220dp，
   保证入口永远在，不会被合集名挤没。

**实测（小米电视4A，0.21.0 / 30）**：

- 封面 315×177 居中，左右各 22dp；两侧不裁；顶沿受光与亮边都在，圆角 12dp 不发"刮角"

- 进度条聚焦：点放大 1.5 倍、整条浮出淡底；左右键快进 5 秒
- 歌手聚焦：提亮 + 白下划线；确认进作者主页
- 爱心聚焦：20% 白圆底 + 放大 1.08，红心仍清晰
- 「下一首」预告在有 / 无两种模式下，控制行位置不变
- 开播放列表落在当前行（第 28 行，红竖条 + 高亮），返回先收列表
- FATAL 0，无异常日志

### 补丁 0.22.0 · 首页跟播放页统一成一套语言

首页从 Phase 9 定稿之后就没再动过视觉：那时它是「一列导航 + 一张小图 + 一张表」，
跟播放页是两套骨架配两种皮肤。这一版把首页换成播放页那一套，
顺手修掉底栏一直存在的一个假 affordance。

**视觉五件**

| 位置 | 原来 | 现在 |
|---|---|---|
| 整页背景 | 纯色 | 当前歌单封面放大模糊 + `home_scrim` 横向渐变遮罩（左 80% → 右 70%），侧栏自身再压 94% 底 |
| 头部 | 178×100 的小图 | 280×158 封面卡：12dp 圆角 + 2dp 常驻亮边 + 顶沿 18dp 受光 |
| 侧栏项 | 选中 / 聚焦两级实色 | 玻璃两级：选中 11%、聚焦 20% + 1.5dp 亮边 |
| 播放全部 | 聚焦翻实心纯白黑字 | 玻璃 17% → 30% + 2dp 亮边 |
| 底栏 | 裸 ImageView + 12sp 灰字模式 | 玻璃方盒；模式改图标 |

**底栏那三颗键原来是按不动的。** prev / play / next 是裸 ImageView，
没有 clickable，`MainActivity` 里也从没引用过——长得像按钮，按下去什么也不会发生。
现在每一颗都真动手。底栏从「展示条」变成「控制条」。

**光标到不了底栏。** 原来从列表第一行去底栏要按三十多下。现在三条路：
列表里按住下键（连续 8 次重复，约 0.9 秒）、列表末尾按下、侧栏走到最后一项再按下。
**单击下键仍是一行一行走**——那条路不能改，改了再也翻不了列表。

**底栏的焦点反馈重做了一遍。** 这一条是量出来的，不是看图看出来的。

| 键 | 原来 | 现在 |
|---|---|---|
| 播放键 | 常态 20% 白、无边；聚焦 30% + 2dp 亮边 | 常态 15%；聚焦 30% + 2dp 亮边 |
| 其余四颗 | 聚焦 15% 白块、无边 | 聚焦 22% 白块 + 1.5dp 亮边 |
| 歌名 | 聚焦 15% 白块、无边 | 聚焦 22% 白块、无边（字不画框） |

实测像素：焦点在播放键时 `#59595B`、其余 `#111114`；焦点在下一首时 `#454548`、
播放键退回 `#343437`。**两态里焦点那颗都是全排最亮的。**

改之前不是这样：聚焦的下一首 `#343538`，播放键常态 `#343437`，两者同值，
只靠一块 15% 的白底区分；而且播放键常态 20% 白比任何一颗的聚焦态都显眼，
「最亮的那颗」根本不代表焦点在哪。

三份底板是底栏专用的（`bg_bar_icon_focus` / `bg_bar_play_glass` / `bg_bar_title_focus`），
没有复用播放页那两份：播放页 0.21.0 定稿了，那边「胶囊常态就是全页最亮」的规则
在底栏不成立——底栏有五颗键并排，都那么亮的话最亮的那颗就不再代表焦点。

**落点改了。** 进底栏时焦点落在**播放键**，不是歌名。歌名底下只垫一块玻璃，
那一排的方盒和亮边一颗都不亮，用户会以为还停在列表里。

**实测（小米电视4A，0.22.0 / 31）**：

- 列表长按下键直达底栏，焦点落在播放键并亮出 2dp 白边（`#59595B`）
- 右移后下一首亮出 1.5dp 亮边方盒（`#454548`），播放键退回暗圆（`#343437`）
- 底栏按上回到列表原来那一行，该行有高亮底块，焦点可见
- 侧栏末项（我的）按下也到底栏
- 底栏确认键分别能暂停、切歌、换模式、收藏；诊断埋点「底栏 播放 / 底栏 下一首」落盘正常
- 头图封面卡 16:9 不裁两侧，顶沿受光与亮边都在
- FATAL 0（崩溃目录只有 11-01、11-02 的旧档，今天零新增）

### 补丁 0.23.0 · 推荐音乐与推荐 UP 主

这一版回答的是「首页进来的第一屏，怎么保证全是歌」。原来的挡法是标题关键词黑名单，
会漏也会错杀；现在改看 B 站自己给稿件打的分区名。

**音乐区十二个二级分区，逐个实测比对出来的**（搜索结果 `typename` 与排行榜 `tname` 交叉验证）：

| 算歌 | rid | 分区 |
|---|---|---|
| ✓ | 28 / 31 / 59 / 193 | 原创音乐 / 翻唱 / 演奏 / MV |
| ✓ | 30 / 130 / 29 / 265 | VOCALOID·UTAU / 音乐综合 / 音乐现场 / AI音乐 |
| ✗ | 243 / 244 / 267 / 266 | 乐评盘点 / 音乐教学 / 电台 / 音乐粉丝饭拍 |

`243 乐评盘点` 在新版分区体系里叫「电台·歌单」，几小时的循环歌单与盘点视频全在这一格，
是长视频的主力来源。这一条比标题匹配可靠一个量级：标题会漏（《XX 精选集》一条都挡不住），
也会错杀（歌名里带「教学」两个字）。

**推荐池** = 音乐区排行榜（`ranking/v2?rid=3`，97 条）+ 分区最新投稿（`newlist?rid=3`，3 页），
交替合并 → 白名单筛分区 → 40 秒 ~ 15 分钟时长闸门 → **随机端出 60 首**。

**为什么要随机**：榜单和新投稿在几分钟内是同一批东西，老实取前六十的话，用户再按一次
「推荐音乐」会拿到一模一样的一屏，那个按钮看起来就是坏的。候选池约一百首，随机取六十，
同一批数据也能端出不同组合。实测连按两次，首行与头图都变了。

**时长为什么只能本地筛**：搜索接口有 `duration`（`1`=0–10 分钟 / `2`=10–30 / `3`=30–60 /
`4`=60+，服务端真实生效——同一关键词不加是 30 条里 21 条超 20 分钟、最长 14 小时，
加 `duration=1` 后 0 条超、最长 458 秒），但 `newlist` / `region/feed/rcmd` / `ranking`
**都不认**它，传了结果逐字节相同。那三条路只能拉回来再丢。

搜索接口还支持 `tids` 按二级分区过滤（纯度 30/30，但**不支持多值**，传 `31,28,59` 返回空）；
将来若要「只搜歌」的入口，这条是最省事的。

**推荐 UP 主没有专门接口**：B 站不提供「推荐音乐人」的公开列表，逐条查 `space/acc/info`
会吃风控（实测连查 14 个，12 个返回 `-352`）。反过来做——从推荐池聚合，
谁在池子里出的歌多谁靠前。零额外请求，并且和推荐音乐永远同源。

**两处标记的取数**

| 标记 | 位置 | 取数 |
|---|---|---|
| 已收藏 | 歌名后 14dp 实心红心 | `FavState` 本地索引，绑定里不发请求 |
| 已关注 | 行尾胶囊 | **拉关注列表在内存比对**：一页 50、最多 6 页 |

已关注本来该用 `x/relation?fids=` 批量问，实测**登录态下返回 -400 请求错误**
（未登录反而返回 -101，所以「没报错」不能当作可用）。逐个查会风控，
最后只剩「拉列表比对」这一条稳的路，代价是关注三百人以上会有遗漏。

**刷新**：推荐池 5 分钟保鲜期；在侧栏**再按一次当前项**是「换一批」。

**侧栏从 9 项变 11 项，行高 36 → 34dp、行距 2 → 0、分组标题上距 12 → 6**。
按老尺寸，十一项连两个分组标题会撑出 540dp 的屏，最后一项被切掉半行——
切成半个字比少一项更像渲染坏了。

**实测（小米电视4A，0.23.0 / 32）**：

- 推荐音乐 60 首，8 条样本时长 0:48 ~ 4:29，无合辑、无盘点、无循环歌单
- 连按两次「推荐音乐」，首行从《临表涕零，不知所言》换成《SMTR25 Official Trailer Film》，
  头图同步更换；诊断日志两次「推荐池」落点
- 推荐 UP 主按曲数降序（4 首 / 3 首 / 1 首…），头像是圆形、列头自动隐藏、「播放全部」置灰
- 「我的收藏」每行歌名后都有红心（同一适配器、同一判据）
- 「已关注」胶囊右对齐、与「N 首」不重叠（临时把整表标成已关注验证渲染，验完已改回）
- 推荐音乐 → 推荐 UP 主 → 推荐音乐 往返，列头恢复、曲目表恢复；5 分钟内命中缓存
- 侧栏十一项完整显示，末项「我的」未被播放条压住
- FATAL 0（崩溃目录只有 11-01、11-02 的旧档，今天零新增）

### 补丁 0.24.0 · 「推荐音乐」换成长合集

0.23.0 解决的是「这一屏全是歌」，0.24.0 换了个问题：**听歌不只是挑歌，还有「让它自己放着」。**
一张六小时的歌单按下去就一晚上不用回来，比三十首单曲更贴合电视这个场景——遥控器在茶几上，
人不在电视机前。

做法一句话：**每次进页面随机抽 3 个关键词 → 各路结果取并集 → 只留一小时以上 → 随机端出 30 首。**

| 参数 | 值 | 为什么 |
|---|---|---|
| `duration` | `4` | 服务端只回 60 分钟以上那一档，拉之前就筛掉 |
| `tids` | `3` | 限定音乐大区；「时长」「网络」「首」这类单字泛词不加它会搜回电视剧解说 |
| `page_size` | `50` | 一步够三十首，省两次翻页 |

实测每个关键词都稳定回 50 条、且全部超过一小时，三路并起来候选在 98~100 条之间。

**关键词之间是或的关系**：58 个词随机抽三个，命中任意一个就进池。同一批词能端出无数种组合，
刷新不必换数据源。实测六轮，抽到的词没有一次重复（`MV/00/80`、`华语/纯音乐/影视`、
`长途/中文/酷狗`、`QQ音乐/酷我/现场`、`黑胶/80/无损`、`台湾/纯音乐/影视`）。

**为什么不加时长上限**：池子里最长的一条是 908 小时的「十一堵车必备歌单」。那不是脏数据，
恰恰是这种内容才值得按一次就不用管——加上限反而会把最合适的那批挡掉。

**为什么没有保鲜期**：需求就是「每次进来换一批」。拿上一轮顶上去，用户只会觉得按了没反应。

### 补丁 0.26.0 · 搜索页改成左键盘 / 右结果

0.15 那版搜索页是「上结果、下键盘」，键盘是 QWERTY。两个问题叠在一起：

### 补丁 0.27.0 · 按一格弹字母，历史只记提交过的词

0.26.0 的九宫格用了「同键连按」：按 `abc` 出 `a`，再按出 `b`，第三次出 `c`。逻辑上省了键，
实际用起来不成立——**遥控器上没有人记得住「这一格刚才按到哪儿」**。想打 `c`，得先知道
上一手是不是刚按过这格；按错了就得退格重来，退格之后计数器又乱了。手机上的拇指键盘靠
「手指还在原处、节奏也还在」撑着，电视上这两个前提都没有。

**改成弹卡挑选。** `abc` 按下去，键盘上浮出一张卡片，把这一格的字母排成一排，光标落在第一个，
左右挑、确认落字。落字后卡片收起、光标回原来那一格，接着打下一个字母。多按一次确认，
换掉的是「数错重来」的全部成本。

**卡片是叠层，不是布局的一部分。** 塞进键盘的 `LinearLayout` 会让键盘腾出一行高度，
按一下整块键盘往上缩一截。做法是布局里给键盘套一层 `FrameLayout`（`panel_search` 与
`overlay_fav_folder` 都改了），`Keypad` 从 `container.parent` 拿这层，把卡片加进去。
底下压 69% 的暗色：全黑看不出自己按的是哪一格，太淡又盖不住下面的键。

**焦点与按键**：卡片出现时 `requestFocus` 到第一个字母；`Keypad.contains()` 同时认容器和卡片，
方向盘才不会漏给 `FocusFinder`（漏出去的表现是「在卡片上按左，光标跳出浮层」）。
左右在字母间移动，上下与返回都是取消——一次返回只退一层，不许顺手关掉搜索页。

**顺带修掉历史被中间态塞满的 bug。** 0.26.0 在 `runSearch` 末尾无条件写历史，而防抖搜索
每停 400ms 就来一次，于是历史里会排出 `q`、`qi`、`qin`、`qing`、`qingt`…… 真机上
打一个 `qingtian` 就留下五条残词。现在只有明确提交（按搜索键、点历史、从结果里起播）才记。

验证（versionCode 36）：按 `jkl` 弹出 j/k/l 且光标在 j；右移到 k 确认后 `k` 落进输入行、
卡片收起、光标回 `jkl`；返回与下键都只取消、不多出字母；遮罩下仍看得出按的是哪一格；
新建收藏夹浮层里同样能弹并落字；历史文件只剩 `zhoujielun / qingtian / yequ`；FATAL 0。

**顺带：播放页的长时长不再写成「分钟数一直涨」。** `NowPlaying.fmt()` 原来固定 `m:ss`，
六小时合集在左下角显示 `418:08`——三位数的分钟位，第一眼读不出是分还是秒，而列表里
同一首歌写的是 `6:58:08`，两处对不上。改成满一小时自动带小时位（`h:mm:ss`），
不足一小时维持 `m:ss`；当前位置与总时长共用这一个函数。

为什么不是「一律带小时」：`0:00:08` 这种写法在短歌上多出两个字符，进度条两端本来就窄，
每秒跳动时更容易看出字宽变化。按是否满一小时切，短歌的观感一点没变。

验证（versionCode 36，真机）：短歌 `4:16` / `4:45` 仍是 `m:ss`；单 P 合集总时长 `1:20:07`；
快进跨过一小时后当前位置 `1:00:58` 也带小时位，两侧同格式。
（快进 5 秒一步，用 `input keyevent 22 ...` 批量发到一小时以上，实测步长准确。）

### 补丁 0.28.0 · 搜索页三处收口（退出落点 / 结果可达 / 历史存得住）

0.26 把搜索页翻成左右两栏之后，真机上留下三个手感问题。三个都不是「少了功能」，
而是**看起来没反应**——最容易被当成卡死的那一类。

**一、退出搜索，光标落在别的页上。** `closeSearch()` 走 `home.returnFocus()`，
它按 `dest` 回到「上一次选过的目的地」。而搜索是 `action` 项，`select()` 直接 return，
从不成为 `dest`——于是退出搜索会把光标送到「音乐」「播放历史」这些地方。
返回键只退一层，退完却换了页。改成 `returnFocus(HomeStage.Dest.SEARCH)`，
落点由调用方指定。

**二、搜索出结果之后，光标进不了右栏。** 两条路都断了：

- 键盘顶行按上走 `focusLastHistory()`，而历史收起时（输入框有字）只把 view 设了 GONE，
  `histViews` 一张都没清。`requestFocus()` 到一个 GONE 的父容器里必然失败，
  旧写法却直接 `return true`——上层以为已经交给历史，`focusSearchResults()` 根本没被调用。
  焦点就此停在一块不可见的容器里：屏幕上没有任何高亮，之后每个方向键都像按在空处。
  现在收起历史时同步清账，方法也返回 `requestFocus()` 的真实结果。
- 最右一列按右，`Keypad.move()` 越界时 `return true`（吃掉），于是光标卡在「清空」上不动。
  改成越界返回 false，由调用方决定：搜索页送进结果区，收藏夹浮层自己吃掉（那边右边没东西，
  放行会穿透到背后的首页）。

另外补了第四条：**按「搜索」提交成功后自动落结果第一行**。按了搜索的人下一步就是挑一首，
让他自己找路过去是这一页最没道理的摩擦；防抖搜索不跳，那时人还在打字。

**三、「搜索历史没保存」。** 文件一直是好的——真机上 `search_history.json` 里十条整整齐齐。

「有字就收历史」的规则顺势把历史整块挡住，用户看到的是空左栏加旧结果，
结论只能是「历史丢了」。现在进页面 `setQuery("") + keypad.setInput("") + 空结果 + 重画历史`。

**容量与展示。** 定十条：540dp 屏减去输入回显和 231dp 键盘，左栏一次只放得下五行；

### 补丁 0.29.0 · 频谱 / 菜单顺序 / 退出确认 / 后台播放 / 响度均衡 / 断点续播

八条需求挤在一个版本里。六条是界面，两条是声音，其中「频谱」把整条音频链路翻了一遍——
它要的不是画一张图，而是**这条路上唯一能拿到 PCM 的位置**。

**一、频谱数据从 AudioProcessor 里拿。**

先排除的三种取法：

| 取法 | 为什么不用 |
|---|---|
| `android.media.audiofx.Visualizer` | 要 `RECORD_AUDIO` 权限；走厂商效果器，T962 上实测拿不到回调 |
| `LoudnessEnhancer` | 同样是效果器，只给一个总响度，分不出频带；这台电视上还报 `EFFECT_NOT_AVAILABLE` |
| 拿 B 站播放地址自己解一遍 | 等于把解码器跑两遍，CPU 与带宽都翻倍，还只能覆盖能拿到地址的源 |

留下的是 Media3 的音频管线：重写 `DefaultRenderersFactory.buildAudioSink()`，把 `AudioTap`
（一个 `BaseAudioProcessor`）塞进 `DefaultAudioSink.Builder.setAudioProcessors()`。
解码器出来的 PCM 先过它、再进 `AudioTrack`，一路只解一次。

两个必须踩住的点：

- **`setEnableAudioFloatOutput(false)` 一定要关。** 开着浮点输出时 `onConfigure` 收到的是
  `C.ENCODING_PCM_FLOAT`，分析器只认 16bit，会返回 `NOT_SET` 把自己关掉。现象不是崩溃，
  是「装好了但频谱一直不动」——这一版在这里卡过一次。
- **输出必须与输入等长。** `queueInput` 里先量 RMS 与峰值、乘上增益，再 `replaceOutputBuffer(n)`
  原样写回；多写少写都会让 `AudioTrack` 的时钟和画面错位。

**二、FFT 自己写，1024 点 radix-2。** 旋转因子与位反转表在构造时算一次，之后每 40ms 一卷。
32 个对数频带覆盖 40Hz~16kHz（线性分段会在低频挤成一团、高频只动一两根），
`-62dB~0dB` 映射到 0~1。渲染侧再叠一层「起得快、落得慢」：上升按 0.6 逼近、下降每帧乘 0.88，
否则 30fps 下一排柱子像在闪。

**三、三处摆放，三种职责。**

- **播放页右栏**（有歌词就让位）：真的跟着音乐动，三种样式可切。
  柱状 32 根按槽宽 `slot * 0.52` 铺满整宽——最初卡了 9dp 的柱宽上限，960dp 宽的一栏只填了左边
  三分之一，右边一大片空白。波形取最近 23ms 的 96 个采样画折线；环形是 32 根放射线绕一圈，
  中心一颗随电平呼吸的点。
- **列表行**（歌手与时长之间，24×14dp）：**不接音频**，5 根正弦相位的柱子循环。
  它回答的是「就是这首」，不是「此刻这个鼓点」；跟着音乐跳会在一列静止的歌词里抢注意力。
  暂停时动画停手、停在最后一帧，初值给一副静态的等化器形状（空数组会塌成五个点，像省略号）。
- **首页底栏**（歌手后 24dp）：有歌词滚歌词，没歌词显示频谱。窄条里一律画柱状——
  环形要一块方形的地，塞进 14dp 只剩一个色点；波形 96 个采样摊在 72 个像素上是一道糊。
  三种样式是给播放页那块大图的。

**四、底栏歌词只在「换句」时改 `text`。** 进度每 500ms 来一次，每次都重设一遍文字，
跑马灯就被打回第一个字，永远滚不到第二句。现在记 `barLyricKey`（歌）与 `barLineAt`（句号），
只有句号变了才写。`android:selected` 不是合法的布局属性（AAPT 直接报错），
跑马灯要的 `selected` 只能在代码里 `isSelected = true`。

**五、其余五条。**

- **菜单顺序**：`Dest` 里 `REC_MUSIC` 排到 `MUSIC` 前面，侧栏第一项变成「推荐音乐」。
- **退出确认**：首页分支的返回键先问 `home.handleKey()`（焦点在列表里时它只把焦点退回侧栏），
  没人接手才进 `confirmExit()`：2.2 秒内二次返回 `finish()`，否则弹提示。
- **后台播放**：`Settings.backgroundPlay` 默认开。关掉时 `onStop()` 里暂停并 `Resume.flush()`——
  不留这一步的话，退到桌面那一刻的进度会丢。
- **响度均衡**：同一个 AudioProcessor 里按块算 RMS，追到 `TARGET_RMS = 0.11`，增益限 0.4~2.5、
  每块最多挪 3%，峰值留 1.5% 余量防削波，静音段（RMS < 0.004）不追。开关关掉时增益恒 1。
- **断点续播**：键是 `bvid#cid`——合集 100 P 共用一个 bvid，按 bvid 存会互相覆盖。
  `< 5s` 不记、离结尾 `< 8s` 不续，临时文件 + `renameTo`，单线程 executor，最多 600 条。

验证（versionCode 38，真机）：日志 `频谱就绪 48000Hz 2ch / 32 频带`、`频谱首帧就绪，最强频带 0.53`、
`响度均衡 增益 ×0.48`；柱状 / 波形 / 环形三张逐张截图确认，柱状铺满整宽；六种颜色循环一圈；
列表行在播放 / 暂停两态都画对；底栏有词换句、无词换频谱；返回键弹提示、二次返回
`mResumedActivity` 变成 `com.gathin.tvhome`；后台播放开时 HOME 后仍持音频焦点（`gain: GAIN`）、
关时日志 `回桌面暂停（设置：不后台播放）`；冷启动续播 `1:06 / 17:36`；FATAL 0。

### 补丁 0.29.1 · 页头副标题只留真约束

页头是「26sp 标题 + 13sp 灰字」两行。九条副标题里六条在复述标题：
`音乐区推荐流` / `播放器队列` / `音乐综合榜` / `音乐区最新投稿` / `云端收藏夹` / `最近听过`。
标题已经说明这一页是什么，第二行只是换个说法念一遍——一屏本来就有封面、列表、播放全部，
多这一行就变成说明书。

保留两条，因为它们承载布局表达不出来的**约束**：

| 页 | 副标题 | 为什么留 |
|---|---|---|
| 推荐音乐 | 随机关键词 · 一小时以上 | 说不清这一页的曲目是怎么捞出来的，用户会以为碰巧搜到长合集 |
| 推荐 UP 主 | 按在推荐池里的曲数排 | 排序依据；不看这句会以为按粉丝数或热度排 |

实现上 `Dest.sub` 允许 0，为 0 时整行 `GONE`。不隐藏而是留空 `TextView` 会带走 6dp
`marginTop`，标题与「播放全部」之间多一条空隙。`strings.xml` 里六条死文案一并删掉
（`home_sub_follow` 本来就没有引用）。

判据写进 `AGENTS.md`（Design & Copy Rules 中文执行版）：删掉这段字，用户还能不能从
标题、分组、间距、对齐、选中态里拿到同样的信息——能就删。

验证（versionCode 39，真机）：七个目的地逐页截图——推荐音乐留约束、其余六页标题下无副标题；
收藏页「新建收藏夹 / 删除收藏夹」工具条位置未变（`GONE` 没有挤动焦点树）；
侧栏 → 列表 → 底栏导航正常；FATAL 0。
