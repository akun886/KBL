# KunPlayer

小米电视4A（Android 6.0.1）上自用的 B 站音频/TV 客户端。Kotlin + View + Media3 ExoPlayer，不用 Compose。

桌面和系统设置里显示的名字是 **B站音乐TV版**（`@string/app_name`）。
KunPlayer 只剩仓库名、包名和日志前缀在用，界面上一处都不出现。

## 当前状态

**0.29.1：首页页头不再把标题念第二遍。**

页头原来是「26sp 标题 + 一行 13sp 灰字」，那行灰字一半在复述：标题写「正在收听」，
下面写「播放器队列」；写「播放历史」，下面写「最近听过」。删掉的六条全是这一类。

留下两条：「推荐音乐」下面的「随机关键词 · 一小时以上」、「推荐 UP 主」下面的
「按在推荐池里的曲数排」。这两句是布局说不出来的**约束**——推荐池怎么捞、按什么排；
其余六条删了不丢任何信息。

`Dest.sub` 现在允许 0，为 0 时整行 `GONE` 而不是留一个空 `TextView`：空控件不占文字，
却还占着 6dp 的 `marginTop`，标题和「播放全部」之间会多出一条说不清的空隙。
判断标准写进 `AGENTS.md`：删掉这段字，用户还能不能从标题、分组、间距、选中态里拿到同样的信息。

**0.29.0：八件事——频谱三处（播放页 / 列表行 / 底栏）、菜单顺序、退出确认、后台播放开关、响度均衡、断点续播。**

前六件看得见，后两件听得见、看不见。八件里最花时间的是频谱：它要的不是一张图，
而是**这条路上唯一能拿到 PCM 的地方**。

- **频谱的数据来自自己写的 AudioProcessor，不是系统的 `Visualizer` / `LoudnessEnhancer`。**
  这两个都挂在厂商效果器上，这台电视（T962）上实测靠不住；`Visualizer` 还要 `RECORD_AUDIO` 权限。
  现在的做法是重写 `DefaultRenderersFactory.buildAudioSink()`，把 `AudioTap` 塞进
  `DefaultAudioSink.Builder.setAudioProcessors()`——解码器出来的 PCM 先过它，再进声卡。
  必须同时 `setEnableAudioFloatOutput(false)`：开着浮点输出，`onConfigure` 收到的是 FLOAT 编码，
  分析器会把自己关掉，现象是「频谱一直不动」。
- **FFT 是自己写的 1024 点 radix-2**，旋转因子和位反转表在构造时算一次；32 个对数频带
  （40Hz~16kHz），`-62dB~0dB` 映射到 0~1。起得快、落得慢（每帧 `*0.88`）：鼓点要看得见，
  退的时候留一条尾巴，否则 30fps 下整排柱子像在闪。
- **播放页：没有歌词时右栏画频谱。** 一首没有字幕的歌，右栏本来只能写「B 站没有为这首歌提供字幕」，
  而那行字回答不了「这首歌现在是什么样」。三种样式（柱状 / 波形 / 环形）与六种颜色都在
  「我的 → 播放设置」里改，改完当场生效。环形是 32 根放射线绕一圈，中心一颗随电平呼吸的点。
- **列表行上的小频谱不接音频，只回答「就是这首」。** 一屏只有一行是正在播的，跟着音乐跳
  会在一列静止的歌词里抢注意力；它现在是 5 根正弦相位的柱子，暂停时停在最后一帧。
  初值给了一副静态的等化器形状——空数组会塌成五个贴地的小点，看着像省略号。
- **底栏那条 36×14dp 的窄条里只画柱状。** 环形要一块方形的地才画得出圈，塞进去只剩一个色点；
  波形 96 个采样摊在 72 个像素上是一道糊。三种样式是给播放页那块大图的，条带里能读出来的只有柱子。
- **底栏：歌手后面空出 24dp，有词滚词、没词显示频谱。** 歌词只在「换句」时才改 `text`——
  每 500ms 重设一次会把跑马灯打回第一个字，永远滚不到第二句。
- **「推荐音乐」挪到「音乐」上面，成了侧栏第一项。** 打开电视想听歌的那一下，落点该在这里。
- **返回桌面要按两次。** 第一次弹「再按一次返回键退出应用」，2.2 秒内再按才 `finish()`。
  退一次就没的话，误按一次就得重新进来、重新起播。焦点还在列表里时，第一次返回只退回侧栏。
- **「返回桌面后继续播放」是个开关，默认开。** 关掉时 `onStop()` 里暂停并写一次进度。
- **响度均衡在同一个 AudioProcessor 里做**：按块算 RMS，追到目标 0.11，增益限 0.4~2.5、
  每块最多挪 3%，峰值留 1.5% 余量防削波；静音段（RMS < 0.004）不追。关掉开关增益恒 1。
- **断点续播的键是 `bvid#cid`，不是 bvid。** 合集 100 P 共用一个 bvid，按 bvid 存会互相覆盖。
  5 秒内不记（还没听出味道）、离结尾 8 秒内不续（接着放等于跳过尾巴）；
  写盘用临时文件 rename，单线程 executor，最多 600 条。

真机验证（versionCode 38，小米电视4A）：日志 `频谱就绪 48000Hz 2ch / 32 频带`、
`频谱首帧就绪，最强频带 0.53`、`响度均衡 增益 ×0.48`；播放页三种样式逐张确认（柱状 32 根铺满整宽 /
波形 / 环形放射线 + 中心点），六色循环一圈；列表正在播那行 5 根柱、暂停时停在最后一帧；
底栏有词换句、无词换频谱；侧栏首项「推荐音乐」；返回键弹提示、2.2 秒内再按退到 TV 桌面
（`mResumedActivity` 变成 `com.gathin.tvhome`）；后台播放开——HOME 后仍持有音频焦点（`gain: GAIN`）；
关——日志 `回桌面暂停（设置：不后台播放）`；冷启动续播 `1:06 / 17:36`；FATAL 0。

**0.28.0：搜索页三处收口——退出回「搜索」、光标能进右栏结果、历史真的存得住。**

三条都是真机上被抓出来的，一条比一条实在：

- **退出搜索光标回到「搜索」那一项。** 搜索是 `action` 项、从不成为当前页，`returnFocus()`
  按默认落点回去，就落到了上一次看过的页面（实测落过「音乐」和「播放历史」）——返回键只退一层，
  退完却换了页，人会以为自己按错了。
- **光标能进右栏结果，四条路全通。** 之前键盘顶行按上会撞到一块 GONE 的历史容器（历史收起时
  只藏了 view、没清登记表），焦点停在没有任何高亮的空处，之后每个方向键都像按在空处；
  最右一列按右则卡在「清空」上不动。现在上、下、右、以及按「搜索」提交后自动跳，都能落到结果第一行。
- **历史真的存得住。** 文件一直写得好好的，问题在**重进搜索页时输入框还留着上次的词**，
  于是「有字就收历史」的规则把历史整块挡住，看到的就是空左栏。现在进页面清空输入与上一轮结果。
  容量定为**十条**，左栏一次显示五行、靠滚动翻完——存了看不见等于没存。

**0.27.0：九宫格改成「按一格、弹出该格字母、挑一个落下」；历史只记真正搜过的词。**

上一版是「同键连按」：按 `abc` 出 `a`，再按出 `b`。那套只适合手机拇指——遥控器上没人
记得住「这格刚才按到哪儿」，换个字母要从头数，数错了还得删掉重来。现在按下去直接弹一张卡，
三个字母摆在眼前，光标落在第一个，左右挑、确认落字。落字后卡片收起、光标回原来那格，接着打下一个。

- **卡片是叠在键盘上的一层**，不占布局：键盘不腾位置，按一下不会整块往上缩。
  底下压 69% 的暗色，看得见自己刚按的是哪一格；卡片沿用键自己的白底黑字，只是大一号。
- **只有「明确提交」才进历史**：按搜索键、点历史、从结果里起播。防抖搜出来的不记——
  不然打到一半停手看眼结果，历史里就会排出 `q`、`qi`、`qin`、`qing` 一屏残词（0.26.0 就是这样）。
- **一次返回只退一层**：卡片开着时，返回和上下键都是「这个字母不要了」，搜索页不会被一起关掉。

真机验证（versionCode 36）：按 `jkl` 弹出 j/k/l、光标在 j；右移到 k 确认，`k` 落进输入行、
卡片收起、光标回 `jkl`；返回与下键都能取消且不多出字母；键盘遮罩下仍看得出按的是哪格；
新建收藏夹浮层里同样能弹；历史文件里只有 `zhoujielun / qingtian / yequ` 三个完整词；FATAL 0。
（0.28.0 又验了一遍，同时把历史容量与滚动定稿，见上。）

**同一版顺手改掉播放页的长时长写法。** 进度条两头原来固定 `m:ss`，六小时合集在左下角写成
`418:08`——分钟位堆到三位，读起来分不清是分还是秒。现在不满一小时仍是 `3:41`，满一小时
自动变 `1:20:07`，与列表里的写法对齐。真机验证（versionCode 36）：`4:16` / `4:45` 短歌不变；
`1:20:07` 总时长、`1:00:58` 的当前位置都带小时位，两侧一致。

**0.26.0：搜索页翻成左右两栏——键盘缩成九宫格放左边，右栏全是结果；搜过的词存下来，点一下就再搜。**

三件事，一件是布局，一件是输入方式，一件是回头路。

- **键盘从 QWERTY 换成九宫格。** QWERTY 是给两只手在桌面上敲的；遥控器只有方向键和确认，
  一行十个键意味着按一次右移一格，「zhoujielun」要按四十来次。九宫格一行三个键，
  横向最多移两次，键也大了一圈——电视上的成本主要在「找」不在「按」。
- **键上写字母，不写「2/3/4」。** B 站搜索吃拼音原文，不认 T9 数字串；数字键还得再配一张映射表，
  而遥控器上那套映射从来没人背得下来。（这一版当时配的是「同键连按」，0.27.0 换成了弹卡挑选。）
- **左栏键盘 + 历史，右栏结果。** 竖排的「上结果下键盘」一屏只看得见三行歌，搜完还得先滚一遍；
  键盘挪到左边只占 400dp 宽，换来整屏高度。
- **历史落在本地，最多十条，最新的在最前。** 存的是词不是结果：结果几分钟就旧了，词永远是对的。
  历史列在输入框下面，光标落在键盘第二排第一格：按上到历史第一条、按确认再搜一次，该词随后挪到最前。
- **输入框一有字，历史就收起来。** 不收的话键盘被挤到屏幕下沿——历史是「进来时」的入口，不是常驻面板。
- **落点是键盘第二排第一格（`jkl`）。** 不是第一格 `abc`（每次进页面要多按一次下），
  更不是「搜索」（第一下想打字母却把空词提交了）。第二排是九宫格的几何中心，往哪边走都只有一格。
- **历史条上按下走出最后一条就进键盘**；键盘最底一排再按下就进结果区第一行。

真机验证（小米电视4A，versionCode 35）：历史按「最近搜过」列在左栏、进页面焦点在 `jkl`；
点历史立刻重搜并收起历史、该词挪到最前；
右栏结果与右栏起播正常；键盘最后一排按下直达结果第一行；FATAL 0。

**0.25.0：「推荐音乐」多了一颗「换一批」；「推荐 UP 主」暂时下线。**
两件事，一件是补手，一件是收手。

- **「换一批」放在「播放全部」前面，是个无字的圆玻璃钮。** 进这一页光标默认就落在它上面：
  这一页唯一的新动作就是它，而「播放全部」本来就能从列表上按住下键直接起播，
  不必让它先占着落点。
- **按下去就是一次全新的三路搜索**，不看缓存——和「每次进来换一批」是同一条路，
  只是不用退出再进来。搜索要两秒，这期间旧的一批留在屏上、底下写「加载中」、
  图标自己转起来：按下去和没按下去长得一样，是最容易被当成遥控器没电的事。
- **刷新失败不清屏。** 手里还有上一批就留着，弹一句「这批没换成，再按一次」——
  一屏旧歌永远好过一屏错误。
- **连按只认最后一轮。** 上一轮还在路上就取消，否则三路 × 好几轮并发，回来的顺序还会乱；
  转到别的页也会停手，动画不会在看不见的地方一直转。
- **「推荐 UP 主」从侧栏拿掉，不是删代码。** 推荐池换成搜索来的长合集之后，
  出歌的人几乎全是搬运号，按曲数排出来的榜首没有意义（0.23.0 那版的池子是排行榜 + 新投稿，
  那时它才成立）。枚举里那一项还在，`hidden` 改回默认就回来。
- 侧栏回到十项，行高从 34dp 复原成 36dp——0.23.0 压到 34 是为了装下十一项，现在装得下了。

真机验证（小米电视4A，versionCode 34）：进页面 1ms 内焦点落在「换一批」；按下去光标不动、
旧屏不闪、图标转起来；三次连按各自端出一批 30 首、无并发错乱；刷新后 30 首全部超过一小时
（最短 60 分，最长 5287 分）；「音乐」页没有这颗钮；播放全部照旧起播 30 首；FATAL 0。

**0.24.0：「推荐音乐」不再推单曲，改成每次进来随机抽关键词搜长合集——一小时以上，三十首。**

听歌场景分两种：挑歌听，和让它自己放着别管。0.23.0 那版解决的是第一种（一屏 60 首单曲），
这一版把「推荐音乐」整格改成第二种：一张歌单六到十小时，按下去就一晚上不用回来。

- **每次进页面都重抽词、重搜，不留缓存。** 需求就是「每次进来换一批」，拿上一轮顶上去
  用户只会觉得按了没反应。代价是每次要等两三秒（三路搜索串行），所以先写「正在取」。
- **58 个关键词，每轮随机抽 3 个，各路结果取并集。** 词与词之间是或的关系——命中任意一个
  就进池。同一批词能端出无数种组合，刷新不必换数据源。实测六轮抽到的关键词没一次重复：
  `MV/00/80`、`华语/纯音乐/影视`、`长途/中文/酷狗`、`QQ音乐/酷我/现场`、`黑胶/80/无损`。
- **`duration=4` 是服务端过滤，正好是 60 分钟以上那一档**（1=0–10min / 2=10–30 / 3=30–60 / 4=60+）。
  拉之前就筛掉，不是拉回来再丢。搜索接口是唯一认这个参数的地方。
- **`tids=3` 限定音乐大区。** 关键词里有「时长」「网络」「首」这种单字泛词，不限定分区会搜回
  电视剧解说。实测每个关键词都稳定回 50 条、全部超过一小时。
- **不加时长上限。** 池子里最长的是一条 908 小时的「十一堵车必备歌单」——这种正是要的，
  不是异常值。六轮候选都在 98~100 条之间，随机取三十。
- **挡掉外语教材。** 关键词里的「英语」「日语」「韩语」配上一小时以上的条件，搜出来最多的是
  单词书——第一屏第一条就是《分类记 18000 英语单词》有声书，十几小时，分区还落在 MV，
  分区闸门挡不住。加了一张只挡「教材/课程/有声书」的短表。
- **「推荐 UP 主」没变。** 它仍然吃 0.23.0 那个单曲池（排行榜 + 新投稿、40 秒 ~ 15 分钟）——
  一列人和一列歌不是一回事，池子分开才各自成立。（0.25.0 起这一页已从侧栏下线，见上。）
- **顺带修掉一个一直存在、只是没人撞见的 bug**：列表左侧那道「正在播」红条按 cid 判定，
  而搜索来源的 cid 恒为 0、队列里没取到地址的歌 cid 也是 0 —— 两边都是 0 时整张表都成立，
  三十行全亮红条。改判据为「cid 非 0 用 cid，否则用 bvid」。红条只在真的播了那一首时才出现。

真机验证（小米电视4A，versionCode 33）：三十首全部超过一小时（最短 60 分，最长 60901 分）；
六轮关键词各不同、每轮整屏换掉；起播一条 6:58:09 的合集，进度条正常走、底栏跟着走；
正在播的那首只有它一行亮红条、其余不亮；「推荐 UP 主」仍是旧池；FATAL 0。

**0.23.0：侧栏多了「推荐音乐」和「推荐 UP 主」，判据从「猜标题」换成「读 B 站自己的分区名」。**

这一版解决的是听歌场景里最烦的那件事：几小时的合辑、盘点、循环歌单混在一堆歌里。
原来的挡法是标题黑名单（`开箱 / 盘点 / 教学 / 教程 / 直播回放…`）——会漏（叫《XX 精选集》
的一条都挡不住），也会错杀（歌名里带「教学」两个字）。现在改看分区。

**音乐区十二个二级分区，能当歌听的八个，明确不是歌的四个。** 这十二个是逐个比对出来的，
不是照文档抄的：

| 算歌 | rid | 分区 |
|---|---|---|
| ✓ | 28 / 31 / 59 / 193 | 原创音乐 / 翻唱 / 演奏 / MV |
| ✓ | 30 / 130 / 29 / 265 | VOCALOID·UTAU / 音乐综合 / 音乐现场 / AI音乐 |
| ✗ | 243 / 244 / 267 / 266 | 乐评盘点 / 音乐教学 / 电台 / 音乐粉丝饭拍 |

`243 乐评盘点` 在新版分区里叫「**电台·歌单**」——几小时的循环歌单和盘点视频全在这一格，
长视频的主力来源就是它。

- **推荐池** = 音乐区排行榜（`ranking/v2?rid=3`，97 条）+ 分区最新投稿（3 页）。两路都带
  `tname`，交替合并之后按上面的白名单筛，再过一道 40 秒 ~ 15 分钟的时长闸门。
- **每次随机端出 60 首，而不是取前 60。** 榜单和新投稿在几分钟内就是同一批东西，
  老老实实取前六十的话，再按一次「推荐音乐」会拿到一模一样的一屏——刷新按钮看起来是坏的。
  候选池大约一百首，随机取六十：同一批数据也能端出不同组合。实测连按两次，首行与头图都变了。
- **时长只能在本地筛。** 搜索接口有 `duration` 参数（`1`=0–10 分钟 / `2`=10–30 / `3`=30–60 /
  `4`=60+，服务端生效），但 `newlist`、`region/feed/rcmd`、`ranking` **都不认**它——
  传了结果逐字节相同。所以这三条路只能拉回来再丢。
- **推荐 UP 主没有专门接口。** B 站不提供「推荐音乐人」的公开列表，逐条查 `space/acc/info`
  会吃风控（实测连查十四个，十二个返回 `-352`）。所以反过来做：从推荐池聚合——
  谁在池子里出的歌多，谁排在前面。零额外请求，而且和推荐音乐永远同源，
  不会出现「推荐页有这首歌，推荐 UP 里却没有这个人」。
- **已收藏**是歌名后面一颗 14dp 实心红心，读 `FavState` 的本地索引，绑定里不发请求。
- **已关注**是行尾一个胶囊。本该用 `x/relation?fids=` 批量问，实测**登录态下返回 -400**
  （未登录反而是 -101，所以「没报错」不能当作可用），逐个查又会风控——最后改拉关注列表
  在内存里比对：一页 50、最多 6 页，代价是关注三百人以上会有遗漏。
- **自动刷新**：推荐池有 5 分钟保鲜期，超过就重拉；在侧栏**再按一次当前项**是「换一批」。
- **侧栏从 9 项变 11 项，行高 36 → 34dp。** 按老行高，十一项连两个分组标题会撑出 540dp
  的屏，最后一项被切掉半行。（0.25.0 起「推荐 UP 主」下线，回到十项、36dp。）

真机验证（小米电视4A，versionCode 32）：推荐音乐 60 首全在 15 分钟内、无合辑；
连按两次首行与头图都变；推荐 UP 主按曲数降序（4 首 / 3 首…）、列头自动隐藏、
「播放全部」置灰；我的收藏每行都有红心；已关注胶囊渲染正常；切走再回来命中缓存；

**0.22.0：首页跟播放页统一成同一套玻璃语言，底栏从「长得像按钮」变成真按键，光标到底栏按一下就到。**

这一版做两件事：把首页的视觉换成播放页那一套，以及修掉底栏一直存在的一个假 affordance。

- **头图换成播放页同款的封面卡**（280×158dp，16:9）：12dp 圆角、2dp 常驻亮边、顶沿 18dp 受光。
  原来是一张 178×100 的小图加几行字，整块读起来是「一个圆角矩形」；现在它是「一张浮起来的图」。
  尺寸比播放页那张 315×177 小一号——这一栏还要放标题、播放全部和五六行歌，头图再长一档，
  一屏就只剩四行，而「今天听什么」需要的是行数。
- **整页铺当前歌单封面的模糊底**，再盖一道横向渐变遮罩（左边压暗、右边放亮）。
  听的是哪张歌单，整页就带一点它的颜色；侧栏自己再压一层 94% 的底，只透色相不透画面。
  换歌单换图，淡入 320ms——硬切会闪一下白。
- **按键全部换成玻璃 + 亮边**：侧栏项、播放全部、底栏五颗键。首页和播放页从此不再是
  一套骨架配两种皮肤。
- **底栏那三颗键原来是按不动的。** prev / play / next 是裸 ImageView，没有 clickable，
  代码里也从没引用过——长得像按钮，按下去什么也不会发生。现在每一颗都真动手：
  上一首、播放暂停、下一首。底栏因此从「展示条」变成「控制条」。
- **播放模式也换成图标**（环形箭头 / 带 1 的环形箭头 / 交叉箭头）。播放页 0.20.0 就换掉了
  三个字，首页这一处还挂着 12sp 灰字——同一个状态在相邻两页长得不一样，是最后要消的一处。
  字只留在 contentDescription 里给读屏用；换档仍飘一句提示，因为三张 22dp 的图三米外
  看得出「变了」，看不出「变成什么」。

**光标到不了底栏，改的是按键逻辑。**

原来从列表第一行去底栏要按三十多下——一行一行走到列表末尾才轮到底栏。

- **列表里按住下键直达底栏**（连续 8 次重复，约 0.9 秒）。单击仍是一行一行走：
  那条路不能改，改了就再也翻不了列表。判定同时认重复次数和 `FLAG_LONG_PRESS`，
  前者管电视遥控器，后者管模拟器与部分输入法。
- **侧栏走到最后一项（我的）再按下**，也落到底栏。侧栏和底栏本来就是屏幕最左、最底的两条边。
- **到底栏之后按上，按原路回去**：从列表长按下来的人回原来那一行，从侧栏下来的人回侧栏。
  两拨人不该被塞进同一个落点。
- **落点是播放键**，不是歌名。歌名是这一排七颗键里最不显眼的一颗（底下垫块玻璃而已），
  焦点停在它上面，那一排的方盒和亮边一颗都不亮——用户会以为还停在列表里。

**底栏的焦点反馈重做了一遍：全排任何时候只有一颗最亮，那颗就是光标。**

这是真机上量出来的，不是看图看出来的。底栏原来用的是播放页那份共用的底板：

| 键 | 原来 | 现在 |
|---|---|---|
| 播放键 | 常态 20% 白、无边；聚焦 30% + 2dp 亮边 | 常态 15%（压暗）；聚焦 30% + 2dp 亮边 |
| 其余四颗 | 聚焦 15% 白块、无边 | 聚焦 22% 白块 + 1.5dp 亮边 |
| 歌名 | 聚焦 15% 白块、无边 | 聚焦 22% 白块、无边（字不画框） |

实测像素：焦点在播放键时它 `#59595B`、其余 `#111114`；焦点在下一首时它 `#454548`、
播放键退回 `#343437`。**两态里焦点那颗都是全排最亮的。**

改之前不是这样：焦点在下一首时是 `#343538`，而播放键常态也是 `#343437`——两者同值，
只靠一块 15% 的白底区分，电视上根本看不出来。改之前那一版还倒过来：播放键常态 20% 白，
比任何一颗的聚焦态都显眼，「最亮的那颗」根本不代表光标在哪。

三份底板是底栏专用的（`bg_bar_icon_focus` / `bg_bar_play_glass` / `bg_bar_title_focus`），
没有直接复用播放页那两份——播放页 0.21.0 定稿了，那边「胶囊常态就是全页最亮」的规则
在底栏不成立：底栏有五颗键并排，都那么亮的话，最亮的那颗就不再代表焦点。

真机验证（小米电视4A）：列表长按下键直达底栏、焦点落在播放键并亮出白边；
右移后下一首亮出白边方盒、播放键退回暗圆；按上键回到列表原来那一行；
侧栏末项按下也到底栏；底栏确认键分别能暂停、切歌、换模式、收藏；
FATAL 0（崩溃目录里只有 11-01、11-02 的旧档，今天零新增）。

**0.21.0：播放页左栏重排成「图 / 字 / 进度 / 键」四段，播放键做成胶囊。**

照云音乐播放页的样子改的。核心动作只有一件：**把歌名从封面上搬下来。**

0.19.0 让歌名骑在封面下沿，是为了让左栏只讲两件事；但那个做法把所有字压在
一条 148dp 的渐变带上，歌名、歌手、收藏、合集四样东西挤同一块地方。
这一版反过来：字整块移出去，封面只负责交代「这是哪首歌的图」。

- **封面 315×177，是原来 420×236 的 3/4，仍按 16:9 取图。** 中间做过一版方卡
  （参考图就是方的），但 B 站的稿件封面是 1920×1080，装进方框要裁掉两侧各四分之一——
  实拍图里两侧的音箱整个消失。图改回横的，只缩不放。
- **左栏从 420dp 收到 360dp。** 图缩到 315 之后，420 的栏里左右各剩 52dp，
  封面和下面四行字各走各的，整块看起来是散的；360 只剩 22dp，图才算「在栏里居中」。
  右栏因此多出 60dp——歌词一行能多放三四个字。
- **圆角 14 → 12dp，顶沿受光 22 → 18dp，亮边 2dp 不动。** 前两个按尺寸比例降；
  亮边降不得——描边的外半被 `clipToOutline` 裁掉，2dp 进去剩 1dp，1.5dp 只剩 1.5 个
  像素，聚焦缩放一动就闪。这条边是常驻的，宁可略重也不能在动的时候断。
- **歌名独占一行，19sp，右侧 44dp 大爱心**，跟封面之间留 20dp。歌名仍然最多两行，
  心用 center_vertical 落在两行中间，不飘。
- **歌手与合集名并成一行**：歌手在前（wrap_content，最长 220dp），合集名在后
  （weight 1，超长自己省略）。合集名单独占一行会多 20dp，而左栏已经贴到屏幕下沿。
- **播放键 44dp 圆 → 84×44 胶囊**（20% 半透明白，圆角 22）。圆在三颗动作键里读作
  「又一个图标」，而它是唯一会被连按的键，该有分量；胶囊一拉长，左右两颗退成卫星。
- **收藏心去掉那层半透黑圆**：它不再压在照片上，底下就是页面底色，再垫一层黑是
  给已经不存在的浅色封面做保护。焦点态改成 20% 白圆底 + 放大 1.08。
- **「下一首」预告改成 16dp 固定高，没有时 INVISIBLE 而不是 GONE**：原来一出现
  就把控制行往下顶 20dp、一消失又弹回去，换歌时整排键上下跳一次，比少两行预告难看。
- **按键说明从左下挪到右下**：左栏从 425dp 长到 459dp，左下角已经没有它的位置，
  而右栏底部那 56dp 本来就是给歌词留的安全区，落在那儿谁也不挡。

参考图里还有两样没画：歌名旁边「极高 / 音效」两个标签（我们没有音质档位可选），
心下面那个数字（没有公开的收藏计数）。没有的东西不画，否则用户会满屏去找那个开关。

真机验证（小米电视4A）：封面 315×177 居中、左右各 22dp、不裁两侧；封面聚焦时环完整闭合、
间隙 10dp、卡放大 2% 后仍不贴环；
进度条聚焦时点放大并浮出淡底；歌手聚焦提亮 + 下划线；爱心聚焦出白圆底并放大；
「下一首」预告有无都不推动控制行；开列表落在当前行、返回先收列表；FATAL 0。

**0.20.0：播放页把「第几首」换成了「哪几首」，歌名能按作者，模式只剩图标。**

五件事，都指同一个方向：这一页上的每个位置只该回答一个问题。

- **「3 / 45」换成播放列表。** 数字只回答「第几首」，列表直接让人换歌。点开之后
  右栏（原本是歌词的位置）换成列表，抬头写「播放列表 · 共 45 首」，右边一个叉收起来；
  收起时歌词原样回来。**同一个位置只站一个东西**——两块同时在屏上，等于把这一页唯一的
  阅读区劈成两半。原来那对「歌词 / 曲目」页签因此作废：页签要常驻一整行高度，
  只能换来两个词，而列表本来就需要一个入口。
- **多 P 合集走同一条路。** 列表里放什么由来源决定：合集放这一张的曲目，其余放播放队列。
  这两件本来就是同一件事——从合集里起播时，队列就是那些曲目。
- **「顺序 / 单曲 / 随机」换成图标**（环形箭头 / 环形箭头带 1 / 交叉箭头）。三个字挂在
  每首歌旁边，等于让人每首都读一遍已经知道的东西；换了哪一档仍然有一次飘字提示。
- **歌名 23sp → 19sp。** 玻璃叠层让歌名成了封面里最重的东西，23sp 会压过图本身。
- **收藏心从封面右上角挪到歌名末尾**，跟歌名最后一行齐底。右上角是「关于这张图」的位置，
  收藏是「关于这首歌」的动作。
- **歌手名可以聚焦，按确认打开作者主页**，到那儿关注。焦点态是提亮 + 下划线——
  这一页不加底板：那块字本来就躺在压深渐变上，再加半透明底就是三道边。

作者主页在叠放顺序里本来在播放页**下面**（它是播放页的来处）。从播放页点歌手进来时
把它提到最上层，返回时再退回播放页，而不是把人甩回首页。

真机验证（小米电视4A）：开列表 → 焦点落在正在播的那一行（红竖条 + 高亮）；点另一首
直接换歌、红条跟着走、列表不关；多 P 合集里切 P 同样成立；返回键先收列表再退页面；
上键到顶走到抬头的叉、下键回到列表；点歌手进作者主页、返回退回播放页；FATAL 0。

**0.19.0：歌名搬到封面上，左栏只剩「一张有字的图 + 一排键」。**

玻璃叠层版。0.18.0 解决了「光和层次」，这一版解决「左栏到底在讲几件事」：
以前是「一张图 · 歌名 · 歌手 · 合集名 · 进度 · 时间 · 下一首 · 一排键」，
眼睛要在八段之间上下跳；现在歌名和歌手骑在封面图的下沿，左栏读完只有两段。

- **封面卡五层压在一张 420×236 上**：图 → 底部压深（148dp，上疏下密，
  顶边全透、中点 70%、底边 98%）→ 顶沿受光 → 歌名歌手 → 亮边。歌名不再另起一行，
  省下的约 80dp 没有分给别的控件，而是让封面长到跟左栏同宽。
- **白字骑在图上要付代价**：压深做到 65% 不够，浅色封面（白发那张）上 14sp 的
  歌手名直接糊进图里；现在是「上疏下密」，且**不给文字加阴影**——阴影会在笔画边缘
  糊出一圈毛边，浅色封面压深之后反而更脏，可读性交给那层渐变。
- **焦点反馈换成卡外一道环**。原来靠「把卡边提亮」，可卡边是画在图上面的：
  浅色封面本身比它亮，提亮等于没提——真机上拿粉色封面逐像素比过，聚焦前后
  边缘只差 3 个色阶。环浮在页面底色上，跟封面什么颜色无关，任何一张图都成立。
  环用 2dp、60% 白、圆角 24dp、离卡 10dp；卡同时放大 2%，所以间隙必须给到 10dp——
  按 8dp 做的时候放大后只剩 4dp，环几乎贴在卡上，看起来像双线框。
- **收藏心浮到封面右上角**，垫一层半透黑圆：白心放在浅色封面上会消失。
  （0.20.0 又把它挪到了歌名末尾：右上角是「关于这张图」的位置，收藏是「关于这首歌」的动作。）
- **播放键从实白圆改成 20% 半透明白**：玻璃版里封面是唯一的重心，一块实心白圆
  会跟它抢，整页出现第二个视觉中心。焦点态加 2dp 亮边并提到 30%。

真机验证：歌名 / 歌手骑图清楚锐利、无阴影毛边；封面聚焦时完整闭合的环，四边都在、
间隙均匀；进度条与收藏的聚焦态都可见；空态（没有歌）封面卡整块收起换成同位置的一段字。

**0.18.0：播放页不再是一块黑板。封面把颜色渗进背景，歌词按距离分层，焦点看得见了。**

三件事，都是光学问题，不是审美偏好：

- **背景的模糊封面一直等于没画。** `player_bg` 是 `alpha=0.1`，上面盖的遮罩又吃掉 82%，
  两层剩 1%——任何封面最后都是同一块 `#17171A`。现在 alpha 给到 0.75，遮罩从
  「均匀压暗」改成横向渐变（左 92% → 右 60%）：左栏压着歌名和时间，不能有光斑；
  右半屏留给封面的颜色。红色封面整屏发红，蓝色封面整屏发蓝，一眼能认出「这是哪一首」。
- **深底上投影是无效的。** 想在 `#17171A` 上让封面浮起来，加 elevation 只会让图发灰——
  黑影子叠黑底没有对比。所以改成受光的边：14dp 圆角、2dp 描边（外半边被
  `clipToOutline` 裁掉，剩 1dp）、顶沿 22dp 的一道 20% 白渐变。焦点态把这道边
  从 20% 提到 60% 再放大 2%，替换掉原来那 1.5% 的缩放——564px 上两端各动 4px，
  三米外没人看得出光标在哪。（这道「提亮边」在 0.19.0 被卡外的环取代了：
  浅色封面上白边抬不过图的白，只有环跟封面颜色无关。）
- **歌词一律 0.55 亮度，隔一行和隔八行一样亮。** 满屏字幕没有落点。现在按
  「离当前行几行」分 1.0 / 0.62 / 0.42 / 0.28 / 0.16，边缘那几行几乎看不见，
  也就不必再叠一层渐隐遮罩——遮罩压在高斯模糊的背景上会露出一条直边，更像渲染错误。
  歌词区上下各收 56dp，首句不再贴着屏幕上沿被 overscan 切掉。

顺手修的：进度条 3dp→4dp 且拖动点常显（原来只在聚焦时冒出来，等于进度平时没有指针）、
已播时间与总时长分开亮度、播放键 56→44dp（白底圆在这一页是唯一实心块，太大就把封面压成配角）、
进度条下面加一行「下一首 · xxx」（顺序模式才画：单曲循环的下一首是它自己，随机的预告不了）。

真机验证：红封面的歌整屏泛红；封面聚焦时白边明显提亮（逐像素对比确认）；焦点顺序
播放键 → 进度条 → 收藏 → 封面 全部可见且不会漏到 overlay 后面；切到单曲模式「下一首」消失。

8 个分 P 里 5 个完全空，能拿到的那条 `ai-zh` 内容是「大蚂蝗每个人都爱吃」——别的视频的字幕，

- **空态只有「暂无歌词」四个字，分不清是内容没有、还是应用没干活。** 现在分五种写：
  没字幕 / 字幕不像歌词已隐藏 / 加载失败 / 登录后显示 / 暂无歌词。

真机验证：田馥甄 P1 →「B 站没有为这首歌提供字幕」；王杰 100 首合集 →
`wbi 空，明文接口拿到 1 条` → `字幕 6 行（lan=ai-zh），可用 0 行，丢弃` →

**0.17.2：收藏里的歌终于有歌词了。**

- **收藏夹、搜索来的条目 `cid` 是 0。** 播放器取流时按 bvid 反查过一次 cid，但没写回队列；

打开应用先到首页：左边一列去处，右边一张歌单，底下挂着正在播的那首。
0.8/0.9 两版把「一屏一首歌」当成了整个应用，于是找歌只能靠上键唤出的抽屉——

### 「正在收听」是什么

它就是**播放器的当前队列**，不是第四个推荐源。你在哪一页起播（或按「播放全部」），
队列就是那一页的那份列表，顺序也一致——所以刚在「流行」起播完再点「正在收听」，
两页必然一模一样：不是串了数据，是同一份东西的两种视角。

0.12.0 这里有个真 bug：`playQueue()` 直接把列表适配器内部的 `ArrayList` 存进了播放器，
而适配器换一页是 `clear() + addAll()` **原地改写**。结果是每浏览一页，队列就被悄悄
换成那一页——「正在收听」永远等于「最后看过的那一页」，底栏却还在放上一首。
现在 `playQueue()` 进来第一件事是 `toList()`，队列与界面彻底分开。

这一栏也不再进首页缓存：缓存住的是「上次进来时的队列」，换过歌单就不作数了。
它也不跟着 `notifyDataSetChanged` 重画——自动下一首只换了播的那首，列表不该滚回顶部，
所以 `onTrackChanged` 比的是 bvid 序列，簇新的歌单才重画。

### 合集：多 P 稿件是一张专辑

音乐区里「一张专辑」最常见的形态就是一个 100 P 的稿件——稿件标题是专辑名，
每个 P 是一首歌。但列表接口把它压成**一条**记录下发，只带 P1 的 cid。
照单全收的话，这张专辑在应用里就是一本书只有第一页，按下一首还得跳到别人家去。

`x/web-interface/view?bvid=` 一次给全所有 P（`pages[]` 带 cid / P 名 / 时长），
100 P 的响应约 8KB，比逐首打 playurl 便宜得多。`net/CollectionApi.kt` 把它包成
`Album`：内存 LRU 8 张 + 磁盘 40 张、24 小时过期；同一个 bvid 并发只打一次接口
（播放器和播放页几乎同时发现「这首属于合集」，各拉一遍就是三次一模一样的 view）。

| 位置 | 表现 |
|---|---|
| 首页列表 | 一行还是一行（不展开成 100 行，列表会被打散），歌名后面挂一个灰色药丸「合集 100 首」 |
| 播放页左栏 | 歌名是 P 名（谁明浪子心 - 王杰），下面一行是合集名（【Hi-Res无损音质】王杰歌曲音乐合集） |
| 播放页右栏 | 「曲目」页签下是整张专辑的 100 首，序号用 B 站的分 P 号 |
| 计数 | 「1 / 100」而不是「1 / 1」 |

三个容易踩的地方：

- **取流缓存的键要从 bvid 换成 cid**。合集里 100 首共用一个 bvid，按 bvid 命中缓存，
  切到第二首拿到的还是 P1 的流地址。
- **正在播的标记要按 cid 判**，不能按 bvid。按 bvid 的话合集那 100 行会整列亮起红条。
- **队列要换、播放头不动**。起播后把队列换成整张专辑，但不重新取流——
  重新取流会把播放头拨回 0，听感上是一句没唱完又从头开始。

判断「这是不是合集」不能靠列表接口给的 P 数：`videos` 字段只有最新发布和历史给，
音乐区、综合榜、收藏夹都不给，而合集恰恰大量出现在收藏夹里。
真正依据是拉回来的 view 结果。展开的请求量与**用户实际听过的歌数**成正比，
不是列表条数——只有起播和冷启动恢复才会触发，浏览列表不会。
另外收藏夹与搜索的条目 `cid` 是 0（列表接口不给），定位分 P 时要用第一页。

右栏翻页签是**长按下键**。两个坑：

1. 长按判定生效后，系统为了模拟长按会继续重复发 DOWN（先 500ms 后每 33ms 一次）。
   这些连发事件落进列表，焦点从刚钉住的第 1 行一路推到第 7 行。修法：长按生效后
   剩余的连发一律吞掉。
2. 曲目表里按住下键本该是「连着往下翻」，长按翻页会让列表只能移动一行。
   修法：焦点在曲目表里时，下键整个归列表；从曲目表回歌词页走「在最上面一行按上」。

焦点在曲目表里时，确认键归列表（按哪行就播哪首），上键归列表（往回选歌），
左右键仍然是上一首 / 下一首——在合集里就是换这一张的下一首。

实测（小米电视4A，2026-11-01）：100 P 合集列表显示「合集 100 首」角标，
单曲行不带角标；播放页合集名 / P 名 / 计数 1/100 都对；曲目表焦点钉在正在播那一行；
选曲后歌名、计数、红竖条同步；左右键在合集内切歌；长按下键翻页签；
按住下键连翻到第 28 行；第一行按上退回歌词页；
50 P 粤语歌合集（来自收藏夹，cid=0）也能展开；
冷启动后角标仍在；应用侧 FATAL 0、冷启动 159ms。

### 歌词

封面在左、歌词在右，同一屏。0.13 试过「同一位置切换」，每次看词都要先按一下，
而这一页本来就空着半个屏幕——不并排是当时以为封面会被挤到 160dp 以下，
0.14 量下来左栏放得下 400dp 的封面还有余量。
0.15 之后右栏还有第二种内容（合集曲目表），页签在两者之间翻，但仍是同一块位置。

每句居中、当前行放大 1.14 倍并转白：歌词是一句一行，居中后整块有个竖轴，
读的时候眼睛不用横着找起点。放大用 `scaleX/scaleY` 而不是 `textSize`——
改字号会改测量高度，居中的那一行自己把行高撑大，滚动位置跟着抖。
没有歌词时右边只留一行「暂无歌词」（14sp / 45% 透明），不空着：
空着的半屏会被读成「没加载出来」。

歌词来自 **B 站的 CC 字幕**（`net/LyricsApi.kt`），不是另一个歌词库：

```
x/player/wbi/v2?bvid&cid    → data.subtitle.subtitles[]   （WBI 签名 + 登录）
取其中文那条的 subtitle_url  → 公开 CDN，裸 GET，不带 Cookie
body[{from, content}]       → from 是秒（两位小数）
```

三个真机量出来的坑：

- **必须登录**。匿名请求返回 `code=0` 但 `subtitles` 是空数组——又一个谎报的空列表，
  和分区推荐流的 `62013` 同类。所以未登录时干脆不请求。
- **字幕 URL 只有约 30 秒有效期**（`auth_key` 首段就是过期时间戳）。
  只缓存解析后的文本，URL 一次都不留；每次播放重新问一次 player 接口。
- **cid 必须是正片 cid**，和 playurl 是同一个坑（多 P 合集用顶层 cid）。

字幕是整段语音识别，带解说的歌单会把「嗨大家好」一起打出来。B 站把**唱的那几行**
用 ♪ 包起来，说话的不包——这是唯一的过滤依据。三道闸门：

| 闸门 | 判据 | 拦住什么 |
|---|---|---|
| ♪ | 只留被 ♪ 包住的 | 解说词、口播（实测 ♪ 覆盖率 98~100%） |
| 条数 | 少于 8 行不算 | 只有几句哼唱的视频 |
| 行距 | 平均 < 500ms/行不算 | AI 逐字切碎 |

拦不住的一类：AI 对整张纯音乐专辑「听」出一套假歌词（「How anne」「那COUPANDA」）。
它稀疏、均匀，去掉符号后的结构指标和真歌词几乎一样（行距 4.8s vs 5.8s、
平均 7.6 字 vs 7.9 字、唯一行 57% vs 61%），统计上区分不出来。
再狠的规则会误杀英文歌——已知问题，接受。

覆盖率本身不乐观：音乐区推荐流 73%、流行榜 40%（2026-11-01 各抽 30 条）。
所以这条链路是「有就显示」：拿不到就留白，只写一行「暂无歌词」。

实测（小米电视4A）：冷启动首屏 158ms，音乐 33 首 / 流行 28 首 / 最新 24 首，
首页停留 `TOTAL` 85MB，连切五个目的地 + 连切五首 FATAL 0 条、`-404` 0 次。

播放器照旧是进程内单例 + 前台服务：界面销毁重建、回桌面、电视休眠都不影响播放。

## 构建

需要 JDK 17 与 Android SDK（platform 35 + build-tools 35.0.0）。

```bash
export JAVA_HOME="C:\Users\Kun\toolchain\jdk-17.0.2"
export ANDROID_HOME="C:\Users\Kun\android-sdk"
./gradlew :app:assembleRelease
```

产物：`app/build/outputs/apk/release/app-release.apk`

release 签名读根目录的 `keystore.properties`（口令）与 `keystore/kunplayer-release.jks`。
两个都在 `.gitignore` 里：**jks 丢了就再也盖不上已装的包，只能卸载重装**，务必单独备份。
缺配置时构建不会失败，会回落到 debug 签名并在日志里报警告。

## 安装到电视

电视开了 ADB 调试后：

```bash
adb connect <电视IP>:5555
adb install -r app/build/outputs/apk/release/app-release.apk
```

`-r` 覆盖安装要求签名一致。换了 keystore 就只能 `pm uninstall` 重装，
数据（登录态、收藏、队列模式）得先用 `run-as` 打包搬过去，步骤见 `docs/kunplayer-tv-plan.md` 的 Phase 6。

用 U 盘装也行（原厂桌面删了之后没有「应用管理」，走文件管理器）。桌面图标两条
intent-filter 都声明了，当贝/Emotn 这类第三方桌面都能扫到。

## 取诊断数据

自用包刻意保留 `debuggable`，就是为了这两条命令能直接用：

```bash
adb exec-out run-as com.kunplayer.tv cat files/diag.log          # 焦点埋点
adb exec-out run-as com.kunplayer.tv cat files/crashes/*.log     # 崩溃记录
```

日志按 32 条一批落盘，回桌面（`onStop`）时把尾巴写掉。上架前必须关掉 debuggable。
